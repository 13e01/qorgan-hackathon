# QORGAN Sentinel — машинное обучение (учебная модель)

> **Главное.** Это настоящая обученная модель XGBoost, но **обученная на синтетических данных** симулятора QORGAN.
> Она не проверялась на реальных измерениях р. Есиль. Её числа — качество на синтетике, а не доказательство точности
> паводкового прогноза. Официальное состояние QORGAN и предупреждения по-прежнему определяет модель правил T2.

## 1. Данные: что есть и откуда

| Источник | Что даёт | Почему не использован в этой версии |
|---|---|---|
| [База данных Казгидромета](https://centralasiaclimateportal.org/kazhydromets-hydrological-database-is-freely-available/) (`meteo.kazhydromet.kz/database_hydro`) | уровни и расходы по гидропостам, 1995–2019 (обработанные — с 2010, обновление раз в год), ссылка на источник обязательна | суточные значения, а не часовые; посты не совпадают с нашими 4 учебными станциями; нет согласованных порогов W/D; выгрузку нужно делать вручную через портал — за время хакатона не выполнено |
| [GRDC, Петропавловск, ID 2911200](https://www.compositerunoff.sr.unh.edu/html/Polygons/P2911200.html) | суточный расход 1965–1984 | только по заявке и соглашению пользователя; старый период; расход, а не уровень |
| [R-ArcticNet, Ishim at Petropavlovsk](https://www.r-arcticnet.sr.unh.edu/Points/P7055.html) | месячный расход | месячное разрешение бесполезно для прогноза на 6 ч |
| Генератор волны QORGAN (`packages/shared/src/simulation`) | часовые ряды 4 станций, сколько угодно эпизодов, известная «истина» | **использован** — синтетика, это прямо указано везде |

Неизвестные датасеты не скачивались. Следующий шаг с реальными данными — §8.

### Как устроен синтетический набор (`ml/dataset/export.ts`)
- 500 случайных эпизодов (seed 2026 — повторный запуск даёт тот же файл байт в байт). Типы: 65 % паводок, 15 % спокойно, 20 % только местные подъёмы.
- Для каждого эпизода случайно: амплитуда (60–380 см), начало и форма волны, базовые уровни (±25 см), пороги станций (±30 см), время добегания (±25 %), ослабление волны, сглаживание, местный приток, дожди у истока перед волной (60 %) и дожди без волны (ложные предвестники), температура, местные подъёмы/спады уровня (`RISE_RATE`), резкие сдвиги (`LEVEL_SHIFT`).
- **Сбои данных, как их видит сервер:** пропуски показаний (у половины эпизодов 1–8 %), разрыв связи станции на 2–10 ч (30 % эпизодов), одиночные выбросы ±55–150 см (половина эпизодов).
- **Метка — будущее событие, а не правила T2:** «измеренный уровень (без сбоев) достигнет порога в часы t+1…t+6». Две цели: опасный порог D и порог «внимание» W. Правила T2 метки не создают — их оценка на тех же данных записывается в строку только для сравнения.
- Отдельный набор `data/ml/official.csv` — официальные сценарии демо (NORMAL, GRADUAL_FLOOD, RAPID_FLOOD × seed 1, 7, 42) с порогами из seed, в обучении не участвует.

Важно понимать: модель учит **устройство нашего симулятора** (линейное добегание волны, трапециевидный паводок). Хорошие метрики означают, что она хорошо выучила эту учебную реку, а не настоящую.

## 2. Признаки (`packages/shared/src/ml/features.ts`)

Один и тот же код считает признаки при подготовке данных и на сервере — расхождения «обучение ↔ работа» нет.
Используются только измерения с временем ≤ asOf (тест: добавление будущих точек не меняет признаки). Уровни — относительно порогов станции, поэтому модель не привязана к станции и переживает изменение порогов администратором. Нет данных → NaN (XGBoost обрабатывает пропуски сам; в интерфейсе — «Нет данных», не ноль).

| Признак | Смысл |
|---|---|
| `level_vs_danger_cm`, `level_vs_warning_cm` | последний уровень минус порог D / W |
| `delta_1h_cm`, `delta_3h_cm`, `delta_6h_cm`, `delta_12h_cm` | изменение уровня за 1/3/6/12 ч |
| `slope_6h_cm_h` | скорость (МНК) по точкам за 6 ч |
| `accel_3h_cm` | ускорение: (изменение за последние 3 ч) − (за 3 ч до этого) |
| `ma6_dev_cm` | отклонение от среднего за 6 ч |
| `data_age_h` | возраст последнего измерения |
| `rain_6h_mm`, `temp_mean_24h_c` | осадки за 6 ч, средняя температура за сутки |
| `up_level_vs_danger_cm`, `up_delta_3h_cm`, `up_delta_6h_cm` | то же для станции выше по течению |
| `up_arriving_6h_cm` | **что «едет» к станции:** изменение уровня выше по течению между моментами asOf−τ+6 и asOf−τ (τ — время добегания из БД). Обосновано моделью добегания QORGAN; будущие точки не используются |
| `up_travel_h` | время добегания τ |

Модель не оценивает (статус `INSUFFICIENT_DATA`), если последнее измерение уровня старше 3 ч — как и T2 (`staleAfterH`).

## 3. Конвейер обучения (`ml/sentinel/`, воспроизводимо)

```bash
npm run ml:setup      # один раз: ml/.venv и пакеты из ml/requirements.txt (xgboost 3.4.1, scikit-learn 1.9.1, numpy, pandas)
npm run ml:dataset    # data/ml/dataset.csv (500 эпизодов, 522 448 строк) и data/ml/official.csv
npm run ml:train      # обучение и оценка ≈ 3 мин → ml/models/sentinel-model.json, ml/reports/evaluation.{json,md}
npm run ml:test       # тесты конвейера (Python)
```

1. Строки, где модель вообще оценивает (свежий уровень): 521 794 из 522 448.
2. **Разбиение по эпизодам в порядке эпизодов 70/15/15** (350 / 75 / 75 эпизодов): эпизод целиком только в одной выборке, соседние почти одинаковые часы одной симуляции не попадают одновременно в обучение и тест. Тест не используется ни для подбора параметров, ни для порогов.
3. Базовые модели: правила T2, «уровень уже выше порога» (без прогноза), логистическая регрессия (медианная подстановка + индикаторы пропусков + стандартизация), случайный лес.
4. XGBoost (`binary:logistic`, `hist`, subsample/colsample 0,8, seed 0): сетка max_depth {3,4,5} × learning_rate {0,05; 0,1} × min_child_weight {1,10}, ранняя остановка по PR-AUC на валидации (40 итераций). Выбраны: D — глубина 4, 113 деревьев; W — глубина 5, 147 деревьев.
5. Порог вероятности — по валидации, максимум **F2** (пропуск опасного события дороже ложной тревоги): D 0,19, W 0,15. Категория ML: HIGH, если P(D) ≥ 0,19; MEDIUM, если P(W) ≥ 0,15; иначе LOW.
6. Абляция: XGBoost без признаков станции выше по течению.
7. Выгрузка: деревья → компактный JSON (пороги в float32, покрытие узлов для SHAP), базовое значение восстанавливается по самой модели. В файл кладутся 40 примеров паритета (признаки, логит, SHAP от XGBoost).

**Почему XGBoost:** на тесте лучший PR-AUC и полнота на «начале подъёма» (см. [SENTINEL_EVALUATION.md](SENTINEL_EVALUATION.md)); случайный лес даёт чуть меньше ложных тревог, но пропускает в 2,7 раза больше начинающихся опасных подъёмов. LightGBM и CatBoost не пробовались — не хотели ставить лишние зависимости, а запас по метрикам между деревьями маленький. Нейросети не применялись: для 17 табличных признаков это не нужно.

## 4. Инференс на сервере без Python

Модель вычисляется на TypeScript (`packages/shared/src/ml/trees.ts`): обход деревьев по правилам XGBoost (float32, `x < порог`, пропуск → `default_left`) и **точный Path-dependent TreeSHAP** (Lundberg и др., 2018) — тот же алгоритм, что `TreeExplainer` пакета `shap` и `predict(pred_contribs=True)` в XGBoost. Тест `apps/server/test/ml-model.test.ts` сверяет логит и все SHAP-вклады с XGBoost на 40 примерах (точность 1e-4) и проверяет свойство «база + Σ вкладов = логит». Пакет `shap` не ставился: XGBoost уже содержит тот же алгоритм, а сервер считает его сам.

Совместимость (`validateModel`): формат и его версия, версия набора признаков, порядок признаков, горизонт, целостность деревьев. Несовместимый файл → `INVALID`, нет файла → `MISSING`; QORGAN работает с правилами T2.

## 5. Как ML встроена (параллельная оценка)
См. [SENTINEL_ARCHITECTURE.md](SENTINEL_ARCHITECTURE.md). Кратко: в транзакции приёма пакета, после оценок T2, на каждую станцию пишется строка `ml_assessments`; предупреждения строятся только по T2 (тест: журнал предупреждений с ML и без ML совпадает полностью).

## 6. Объяснение («Почему такой риск?»)
- Объясняется та из двух моделей, что определила категорию (HIGH → модель D, иначе — модель W).
- Показываются 3–5 признаков с наибольшим |SHAP|: стрелка (повышает / понижает оценку), значение признака, подпись и фраза, выбранная **по знаку и величине фактического значения** (`apps/web/src/lib/explain.ts`), например «За 3 ч уровень вырос на 27 см».
- Краткое объяснение: категория и вероятность + две главные фразы в сторону итоговой оценки.
- Каждый блок подписан: учебная модель, синтетические данные, SHAP — вклад в оценку модели, а не причина; вероятность — не гарантия; официальное состояние — по правилам.

## 7. Ограничения
- Синтетика из того же генератора, что и демо: на официальных сценариях модель видит знакомую «физику». Это не проверка на реальной реке.
- Горизонт 6 ч: модель не заменяет «Прогноз по реке» (до 119 ч) и фактор волны сверху T2 (до 72 ч). Поэтому у станций ниже по течению ML часто ниже правил (правила уже предупреждают о волне в 51 ч, ML — нет). Это разные вопросы, интерфейс показывает расхождение.
- Вероятности хорошо откалиброваны на синтетике (ECE ≈ 0,001), но для средних интервалов 0,1–0,8 модель слегка занижает частоту событий.
- Осадки и температура в генераторе на уровень не влияют (кроме сценарной связи «дождь перед волной»), поэтому модель почти не опирается на них.
- Казахские тексты объяснений требуют проверки носителем языка.

## 8. Что сделать с реальными данными
Выгрузить уровни постов Казгидромета по Есилю (с указанием источника), построить часовые или суточные ряды, задать пороги постов, пересобрать набор той же функцией признаков (`computeFeatures` работает с любым шагом), переобучить с разбиением **по годам** паводков и сравнить с T2 на тех же годах. До такой проверки модель остаётся учебной.
