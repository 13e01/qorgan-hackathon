# QORGAN — Архитектурные решения (ADR)

Формат: решение · почему · альтернативы · влияние на сроки. Ссылки `ТЗ §n` — на [расшифровку ТЗ](tz/TZ-TRANSCRIPT.md). ТЗ §6 разрешает команде выбирать стек самостоятельно.

### ADR-001. Монорепозиторий на npm workspaces — принято
- `apps/server`, `apps/simulator`, `apps/web`, `packages/shared`; один `npm install`.
- **Почему:** общие типы и модуль риска без копирования; одна команда запуска для новичка. **Альтернативы:** pnpm/turborepo — лишняя установка.

### ADR-002. Backend: Node.js 24 + TypeScript + Fastify — принято
- **Почему:** один язык с фронтендом; `fastify.inject()` для интеграционных тестов без сети; встроенные схемы. `tsx` в разработке, `tsc` для сборки, `zod` для проверки входных данных.
- **Альтернативы:** Express (есть в примерах ТЗ, но меньше встроенной валидации), NestJS (тяжёлый для 2 дней). Fastify в примерах ТЗ нет, но стек свободный.

### ADR-003. SQLite через встроенный `node:sqlite` — принято
- Проверено 2026-10-28: работает в Node 24.22.1 без флагов, SQLite 3.53.4. SQLite есть в примерах ТЗ §6.
- **Почему:** нет компиляции нативных модулей на Windows (главный риск `better-sqlite3`), один файл, бэкап `VACUUM INTO`. Без ORM — SQL-миграции, проще объяснить.
- **Запасной вариант:** `better-sqlite3` (≈30 мин на замену).

### ADR-004. Frontend: React 19 + Vite + TypeScript + MapLibre GL + Recharts — принято (уточнено в T4: без Tailwind и Zustand, см. ADR-022)
- React и MapLibre прямо названы в ТЗ §6. Zustand — живой снимок; `lucide-react` — иконки; без тяжёлых UI-библиотек.
- Карта: стиль OpenFreeMap `dark` (без ключа, проверен HTTP 200) + встроенный GeoJSON реки из OSM как офлайн-запас.
- Адаптивность до 375 px обязательна (ТЗ §7, §9).

### ADR-005. Источник телеметрии — отдельный процесс, данные только через REST API — ⚠️ заменено ADR-017 (T3)
- Симулятор (`apps/simulator`) шлёт `POST /api/telemetry` с токеном устройства и читает команды из `GET /api/simulation/control`.
- **Почему:** ТЗ требует поток «датчик/симулятор → API → backend → БД»; тот же API подойдёт для ESP32; падение симулятора видно как OFFLINE (надёжность, BON-003).
- **Альтернативы:** MQTT — нужен брокер (лишняя установка); симулятор внутри сервера — нарушает схему ТЗ.
- **Сроки:** +≈0,5 ч к T3 по сравнению с встроенным симулятором.

### ADR-006. Универсальная модель измерения `станция · время · параметр · значение · единица` — принято (ТЗ §5.2)
- Справочник параметров с единицами и допустимыми диапазонами; у станции — свой набор показателей и порогов.
- Хранятся оба времени: `measured_at` (модельное) и `received_at` (реальное, для «времени последнего сообщения»).

### ADR-007. Модуль риска: прозрачные баллы по 5 факторам + МНК-тренд — принято (базовый вариант ТЗ §5.4)
- Факторы: уровень, тенденция/ETA, осадки, температура (снеготаяние), волна с верхней станции. Коэффициенты в `risk_config`, их меняет админ (ТЗ §5.7).
- Прогноз уровня с явным горизонтом **3 ч** + ETA до опасного порога с диапазоном неопределённости.
- **Почему не ML:** нет данных для обучения и оценки качества; ТЗ прямо запрещает выдавать условный индекс за научный прогноз. Прозрачный алгоритм проверяется тестами с точными числами.
- Модуль — чистые функции в `packages/shared/risk`, вызывается backend'ом («модуль внутри backend допускается», ТЗ §6).

### ADR-008. Детерминированный симулятор с хеш-шумом — принято
- Шум = `hash(seed, станция, параметр, тик)`: любой тик воспроизводим без хранения состояния → повтор демонстрации (ТЗ §9) и продолжение после перезапуска.
- 1 тик = 1 ч модельного времени; частота отправки 250–5000 мс (ТЗ §5.2 «настраиваемая частота»).
- Задержка волны — реальные расстояния по руслу (OSM) / учебная скорость 3 км/ч.

### ADR-009. Одна транзакция на пакет: запись → риск → предупреждения — принято
- Нет частично обработанных пакетов; `UNIQUE` исключает дубли измерений и активных предупреждений; при ошибке симулятор повторяет пакет.

### ADR-010. REST для команд, WebSocket для рассылки — принято
- ТЗ §5.3 рекомендует WebSocket/SSE. Команды через REST дают понятные коды ошибок; WS остаётся простым.

### ADR-011. Авторизация: 3 роли, cookie-сессия, scrypt, предсозданные учётки — принято (ТЗ §4, §5.1)
- Гость без входа; operator и admin входят. Пользователей создаёт админ (CRUD, ТЗ §5.7); регистрации и OAuth нет.
- Матрица доступа — ARCHITECTURE §10 (толкования INT-001, INT-002 в REQUIREMENTS).

### ADR-012. Статусы предупреждения NEW → VIEWED → RESOLVED + флаг активности условия — принято (ТЗ §5.6)
- Отметки оператора отделены от того, действует ли опасное условие; снятие условия — после 3 спокойных пакетов (защита от «мигания»).

### ADR-013. Демо-запуск: backend + симулятор одной командой, порт 3000 — принято
- `npm start` / `start-demo.bat` поднимает оба процесса; фронтенд собран и отдаётся backend'ом.

### ADR-014. Бонусы: многоязычность, зона риска + сравнение прогонов, устойчивость к сбоям — принято
- Выбраны те, что вытекают из основной архитектуры и не требуют оборудования/платных сервисов (ТЗ §8). Docker и публичный деплой — только при запасе времени (Docker не установлен). Telegram/ML/ESP32 — нет.

### ADR-015. Презентация — слайды в конце дня 2 — принято (ТЗ §10)
- Делаются по готовому продукту (скриншоты настоящего интерфейса), формат выбираем в T11.

### ADR-016. Запуск TypeScript через tsx без шага сборки backend — принято (T1)
- **Почему:** меньше движущихся частей; `@qorgan/shared` импортируется из исходников; `tsc` используется только для проверки типов (`npm run typecheck`).
- **Сроки:** экономит настройку сборки; фронтенд всё равно собирается Vite в T4.

### ADR-017. Встроенный симулятор, данные — через HTTP-маршрут `POST /api/telemetry` в том же процессе — принято (T3)
- **Решение:** исполнитель симуляции живёт в backend и отправляет каждый пакет через `app.inject('POST /api/telemetry')` со своим токеном. Маршрут, аутентификация, проверки и транзакция — те же, что для внешнего устройства.
- **Почему не отдельный процесс (ADR-005):** один источник виртуального времени (БД), один таймер, нет рассинхронизации команд «пауза/стоп» между процессами, детерминированные быстрые тесты с ручным планировщиком; на защите запускается одна программа. Требование ТЗ §5.3 «телеметрия через backend API (HTTP/REST)» выполняется: данные проходят HTTP-маршрут. Внешнее устройство использует тот же маршрут по сети.
- **Последствия:** нельзя показать «симулятор на другом компьютере» без доработки (нужен только HTTP-клиент с токеном станции — T6/T8).

### ADR-018. Модель времени: реальное (`now()`) и виртуальное (часы прогона) не смешиваются — принято (T3)
- Виртуальное время = `sim_start + current_tick × 60 мин`, двигается только тиками; реальное — единственный источник `now()`. Скорость (`tick_ms`) меняет только паузу между тиками, поэтому физика и задержки волны не зависят от ускорения.
- `asOf` оценки риска = часы прогона, а не последнее измерение; ответы содержат `context.mode` (LIVE / PAUSED / HISTORICAL / NO_DATA).
- Подробно — ARCHITECTURE §6.0.

### ADR-019. Калибровка сценариев под модель риска — принято (T3)
- **Проблема 1:** при суточном колебании 3 см и шуме ±2 см наклон доходил до 0,8 см/ч > ε = 0,5 см/ч. В сочетании с фактором потепления (+1) риск «мигал» LOW ↔ MEDIUM на спокойной воде (до 22 переключений за прогон). **Решение:** колебание 1 см, шум ±1 см. Теперь переходы ровно LOW→MEDIUM→HIGH→MEDIUM→LOW (RAPID) и LOW→MEDIUM→LOW (GRADUAL). Модуль риска T2 не менялся.
- **Проблема 2:** в GRADUAL_FLOOD с амплитудой 180 см у QRG-04 (задержка всего 17 ч) на один тик складывались уровень ≥ W (+2), рост с ETA ≤ 24 ч (+2) и MEDIUM у верхней станции (+1) = 5 → HIGH. Это правильная работа правил, но противоречит назначению сценария «постепенный паводок». **Решение:** амплитуда 170 см; проверено на 4 seed.
- **Замечание для T5/T6:** фактор «волна сверху» продолжает действовать, когда волна уже пришла на станцию (частичный двойной учёт). Это не ошибка кода, а свойство правил; при необходимости админ уменьшает вес `upstreamMedium`/`upstreamHigh`.

### ADR-020. Ручное вмешательство — со следующего тика, три типа — принято (T3)
- `LEVEL_SHIFT` и `RISE_RATE` меняют модель реки (передаются вниз по течению), `MANUAL_READING` — одно показание с источником `manual`. Все действуют с `current_tick + 1`: прошлое не переписывается, автомат и ручной ввод не конфликтуют (одна запись на станцию/параметр/тик). Вмешательства хранятся и учитываются при воспроизведении.

### ADR-021. Собственный модуль переводов вместо i18next — принято (T4)
- Три словаря TypeScript (`ru.ts` — эталон, `kk.ts` и `en.ts` типизированы теми же ключами), подстановка `{параметров}`, перевод кодов причин T2 с переводом сантиметров в метры. ~100 строк вместо двух зависимостей; полнота ключей и совпадение подстановок проверяются тестом.

### ADR-022. CSS с дизайн-токенами и React Context вместо Tailwind и Zustand — принято (T4)
- **Почему:** интерфейс небольшой (4 страницы); токены в `:root` дают единый стиль без сборочных плагинов; состояние — один провайдер (`state/store.tsx`) и чистый редьюсер (`state/live.ts`, покрыт тестами). Меньше зависимостей — меньше рисков на Windows.

### ADR-023. Разделение «локальная обстановка / угроза сверху» вычисляет сервер — принято (T4)
- `describeSituation` (`packages/shared/src/risk/situation.ts`) раскладывает готовую оценку T2: статус уровня относительно порогов, тренд, баллы местных факторов и фактора «волна сверху», данные верхней станции. Добавлено в снимок WebSocket и ответы `/risk`, `/risk/explanation`. Ядро T2 не менялось; прибытие волны не утверждается — только «угроза сверху» и фактический локальный уровень.

### ADR-024. Главное число уровня — последнее измерение, а не уровень из оценки — принято (T4)
- Найдено при проверке в браузере: после ручного сдвига +100 см датчик показал 398 см, а интерфейс — 300 см (T2 справедливо не принял ещё неподтверждённый скачок и оценивал по прошлому значению). Теперь крупно показывается измерение, а расхождение с уровнем в оценке — отдельной пометкой (`lib/level.ts`).

### ADR-025. Одна команда разработки и один порт для показа — принято (T4)
- `npm run dev` (`scripts/dev.mjs`) запускает backend и интерфейс, Ctrl+C останавливает оба (на Windows — деревом процессов). Порт backend задаётся явно (3000): при проверке выяснилось, что внешняя переменная `PORT` переносила backend на порт интерфейса.
- `npm run build` + `npm start`: Fastify (`@fastify/static`) отдаёт собранный интерфейс и API с одного адреса :3000.
- Фоновый поток MapLibre подключается явно (`setWorkerUrl` + импорт `?url`) — иначе в режиме разработки Vite ломал путь к нему.

### ADR-026. Редизайн T4.1: свои токены и компоненты вместо UI-библиотеки — принято (T4.1)
- Темы — атрибут `data-theme` на `<html>` и CSS-переменные; тема ставится до первой отрисовки (скрипт в `index.html`), «как в системе» следит за `prefers-color-scheme`. Карта меняет стиль подложки (OpenFreeMap positron / dark), графики берут цвета из тех же переменных (`usePalette`). Новых зависимостей нет.
- Progressive disclosure на нативном `<details>` (клавиатура и экранные дикторы без доп. кода). Переключатели языка и темы — `radiogroup` со стрелками.
- Настройки интерфейса (язык, тема, панель, демо) — только в `localStorage`, сервер о них не знает.

### ADR-027. «Демо за 2 минуты» — рассказ поверх настоящего прогона, без своей симуляции — принято (T4.1)
- `lib/demo.ts` (без DOM и React) запускает RAPID_FLOOD, seed 42, 500 мс/ч одной командой `POST /api/simulation/start` (сервер создаёт и запускает прогон атомарно). Своих таймеров нет: этап выводится из снимков WebSocket.
- Этап включается только при подтверждении данными, по порядку, не больше одного за час симуляции и без отката. «Волна ниже по течению» — только при **местном** подъёме у нижней станции (угроза сверху не считается).
- Найдено интеграционным тестом: на 2–3 первых точках тренд T2 может назвать ростом обычные колебания ≈1 см/ч (QRG-03 на 2-м часе). Модель T2 не меняли; демо считает подъёмом рост тренда 3 часа подряд (`RISE_CONFIRM_H`) или уровень выше порога.
- Активный прогон молча не уничтожается: диалог «показать текущий» / «остановить и начать демо». Выход останавливает прогон демо (данные остаются). Все команды симулятора идут через общий `CommandGate` — двойной запуск невозможен.
- Тот же контроллер проверяется на настоящем сервере (`apps/server/test/guided-demo.test.ts`).

### ADR-028. Предупреждения — в той же транзакции, что и оценка; снятие по истории оценок — принято (genesis)
Предупреждение создаётся/обновляется в `ingest` сразу после сохранения оценок риска: оно не может появиться без оценки или потеряться при сбое. «Три LOW подряд» считаются по сохранённым `risk_assessments`, без отдельного счётчика. Обострение MEDIUM → HIGH возвращает обработанное предупреждение в NEW: нужна новая реакция. Остановка/завершение/сброс прогона закрывают активные предупреждения событием `CLEARED` с комментарием `RUN_ENDED`. Журнал по умолчанию показывает «требуют внимания» (не обработаны), а не только активные: в браузере нашли, что условие снималось, пока оператор писал комментарий, и запись исчезала из списка.

### ADR-029. Администрирование влияет на систему сразу — принято (genesis)
Симулятор и модуль риска читают станции, пороги и `risk_config` из БД на каждом тике, поэтому изменения админа действуют со следующего расчёта (проверено тестами). Станции не удаляются физически (DELETE = `disabled`). Пользователь с историей действий не удаляется (409 `USER_HAS_HISTORY`) — журналы должны оставаться полными. Смена роли/пароля/отключение закрывает сессии.

### ADR-030. Главное отличие — «Прогноз по реке» (QORGAN-ROUTE-1) — принято (genesis)
Маршрутизация измерений верхних станций вниз (lag-and-attenuate) с поправкой по текущей ошибке, каскадом по цепочке, эмпирическим диапазоном и проверкой на истории против persistence и против ETA модели T2. Категорию опасности не меняет. Выбрано из 6 вариантов (docs/INNOVATION.md §2): максимальная польза оператору при данных, которые уже есть. Тренд истока вниз по течению не передаётся (иначе горизонт растёт за счёт малонадёжной экстраполяции). До начала наблюдений уровень верхней станции считается равным первому измерению — с пометкой `assumedHistory`.

### ADR-031. ИИ (LLM) не используется — принято (genesis)
Ключ DeepSeek не запрашивался. Ни одна выбранная функция не требует LLM; LLM не должна определять уровень опасности; система обязана работать без интернета. Автобрифинг через LLM отклонён (риск неверных рекомендаций, внешняя зависимость).

### ADR-032. Публичное размещение: VPS + Docker Compose + Caddy, строгий режим PUBLIC_DEPLOYMENT — принято (genesis)
SQLite нужен постоянный диск — бесплатные PaaS без диска не подходят. `PUBLIC_DEPLOYMENT=true` включает Secure-cookie, trustProxy и отказ запуска с демо-паролями/слабым секретом. Ограничение попыток входа — в памяти процесса (достаточно для одного экземпляра). Docker на ноутбуке не установлен: образ не собирался, проверен только запуск сервера с теми же переменными.

### ADR-033. Внешний датчик: Python + MQTT, брокер Aedes, один источник на прогон — принято
Организатор устно ожидает отдельный датчик, а не «просто API». Выбран MQTT (стандарт для датчиков; QoS 1, завещание). Брокер — Aedes 1.2.0 (MIT, Node.js): Mosquitto для Windows требует системной установки. Брокер — отдельный процесс, только 127.0.0.1, без анонимного доступа; пароль устройства сверяется с SHA-256 в БД (только чтение). MQTT-адаптер передаёт данные через `POST /api/telemetry` (`app.inject`), чтобы не дублировать проверки, риск и предупреждения. Один источник на прогон (`EXTERNAL_SENSORS` / симуляция) — простое и проверяемое правило против смешивания данных. 1 показание = 1 час модели: модель T2 почасовая, ядро не менялось. Доставка: QoS 1 + статус QORGAN (`server/status`) + постоянная сессия подписчика + дедупликация по `bootId`/`seq` — каждая часть закрывает найденный реальной проверкой сбой.

### ADR-035. QORGAN Eclipse: визуальная система «Живая река», только интерфейс (2026-10-29)
- **Контекст:** интерфейс T4.1/Genesis работал, но главная панель была набором карточек; движение паводка вдоль реки было трудно увидеть.
- **Решение:** карта — главный объект главной панели; новая схема «Живая река» (`lib/flow.ts`, `RiverFlow.tsx`) показывает станции по течению и состояние связей (спокойно / угроза идёт / подъём дошёл) **только по `situation` из снимка сервера**; на карте те же связи (бегущий пунктир вниз по течению). Токены обеих тем переписаны, слой компонентов — `src/eclipse.css`. Навигация — боковая с группами (Navbar Gallery: для панелей с многими разделами — sidebar). Подробно — [ECLIPSE_DESIGN.md](ECLIPSE_DESIGN.md).
- **Новая зависимость:** `@fontsource-variable/inter` 5.3.0 (OFL-1.1) — Inter с осями wght/opsz и казахскими буквами; файлы шрифта входят в сборку, поэтому интерфейс одинаков на любом ноутбуке и **работает без интернета** (Google Fonts потребовал бы сеть на защите). Браузер загружает только нужные наборы символов (кириллица ≈ 30 + 42 КБ).
- **Отклонено:** motion/react (все анимации — CSS и один хук на `requestAnimationFrame`, библиотека не дала бы пользы); фоновое видео (нагрузка на ноутбук, права на контент); зоны затопления (нет рельефа и гидравлической модели — это было бы выдумкой).
- **Не менялось:** сервер, `packages/shared`, Python-датчик, MQTT, БД, API, WebSocket, BAT-файлы.

### ADR-034. Подготовка чистого демо, счётчики по прогонам, модель датчика с целями, BAT только ASCII (2026-10-29)
- **Контекст:** после ручной проверки на Windows BAT-файлы падали (UTF-8 + LF), датчик в DANGER рос без предела (14,54 м), счётчики устройства копились за всё время, а журнал `device_log` (одна запись на причину за 10 с) не давал разбивки «20 отклонённых».
- **Решение:** (1) BAT — только ASCII и CRLF, единый `start-demo.bat` с порядком «сервер → брокер → датчик» и `stop-demo.bat`, который ищет окна по командной строке (`scripts/stop-demo.ps1`, встроенный PowerShell — новых зависимостей нет); (2) таблица `device_run_results` (миграция 4) — каждое сообщение по прогону и итогу, общие счётчики не сбрасываются; (3) «Подготовить чистое демо» — интерфейс над существующими командами `stop` и `external/start`, без удаления данных; состояние уровня относительно порогов (`lastLevel`) считает сервер; (4) модель датчика ведёт уровень к учебной цели режима с ограниченным шагом; второй экземпляр датчика блокируется файлом.
- **Почему не сброс счётчиков/истории:** требование «не удалять историю незаметно»; новый прогон уже даёт чистые измерения и предупреждения, а счётчики по прогону — чистые числа без потери общих.
- **Ограничение:** часы прогона датчиков идут по реальному времени от старта прогона (1 час модели = 2 с); если прогон долго стоит без показаний, время модели «убегает» — поэтому перед показом начинают новый прогон.

### ADR-036. Eclipse Cinematic: прототипы главной страницы без анимационных библиотек; шрифт Source Serif 4 (2026-10-29)
- **Контекст:** нужен самостоятельный кинематографичный вход в продукт; перед полной реализацией — три прототипа первого экрана (`#/concepts/a|b|c`) для выбора направления. Изучены Motion, Motion Primitives, Magic UI, Aceternity UI, hover.dev (docs/ECLIPSE_CINEMATIC_RESEARCH.md).
- **Решение:** (1) **Анимационные библиотеки не ставим.** Magic UI, Motion Primitives, Aceternity и hover.dev требуют Tailwind + shadcn + `motion`; Aceternity и hover.dev ещё и запрещают распространять исходники. Нужные эффекты (маски строк, слова с размытием, счёт чисел, рисование SVG-линий, появление при прокрутке) сделаны на CSS `@keyframes`, `IntersectionObserver`, `requestAnimationFrame` и Canvas 2D — 0 КБ зависимостей. `motion` (MIT, ≈ 29 КБ с `LazyMotion`) — кандидат для финальной страницы, только если понадобятся анимации выхода или связка с прокруткой. (2) **Шрифт `@fontsource-variable/source-serif-4` 5.3.1** (OFL-1.1, Adobe): антиква для концепции C; подмножество cyrillic-ext содержит казахские буквы (ә ғ қ ң ө ұ ү һ і), проверено в браузере; файлы шрифта загружаются только на страницах прототипов. (3) Прототипы — отдельный файл сборки (`React.lazy`): рабочее приложение их не загружает. (4) Общие правила `prefers-reduced-motion` в `styles.css`/`eclipse.css` больше не действуют внутри `.cine`: там движением управляет `data-still` — по той же системной настройке или переключателю на панели прототипа (нужно, чтобы на компьютере с выключенными эффектами Windows можно было оценить анимацию).
- **Честность данных:** все цифры и состояния на прототипах — из снимка сервера (`riverFlow`, метаданные станций), время добегания и пороги — из БД; бейдж «Демо-данные · учебная модель» на каждом экране; линия реки — OSM, горизонтали в A — декоративный шум, усиление изгибов в B — подписанная схема.

### ADR-037. Hydro Future — главная страница по адресу «/», отдельные файлы сборки (2026-10-29)
- **Контекст:** пользователь выбрал концепцию B (анимированную). Нужна законченная главная перед рабочей системой.
- **Решение:** (1) `/` и `#/` — главная; все разделы системы сохраняют свои адреса; старые `#/concepts…`
  перенаправляются на `#/`. (2) `Root.tsx` загружает главную и систему отдельными файлами (динамический `import`),
  CSS карты подключается только в системе — главная не грузит MapLibre и Recharts. Крупные библиотеки выделены
  (`maplibre`, `react`); порог предупреждения Vite возвращён к стандартным 500 КБ — его превышает только готовый
  файл `maplibre-gl`, который разделить нельзя. (3) Переход — View Transitions API без библиотек; при «меньше
  движения» — мгновенно. (4) Анимационные библиотеки по-прежнему не используются (ADR-036): сцена — свой класс
  `RiverScene` на Canvas 2D, остальное — CSS. (5) Переключатель анимации убран: движение — только по системной
  настройке `prefers-reduced-motion`. (6) Зависимость `@fontsource-variable/source-serif-4` удалена — она была
  нужна только отклонённой концепции C.
- **Последствия:** снимки экрана в разделе «Настоящая система» — статичные файлы, их нужно переснимать при заметных
  изменениях интерфейса. Общие имена классов главной — только внутри `.cine` (класс `.reveal` есть и в панели).
