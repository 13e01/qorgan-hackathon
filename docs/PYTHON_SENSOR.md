# Python-датчик и MQTT

Отдельная программа на Python работает как физический датчик уровня воды: **сама** генерирует показания и передаёт их по MQTT. QORGAN принимает их через тот же приём телеметрии, что и все источники: проверка → SQLite → модель риска T2 → предупреждения → WebSocket → сайт.

> MQTT выбран нами как стандартный протокол для датчиков. Организаторы его **не требовали**; устно было сказано, что связь датчика с сервером не должна быть «просто апишкой».

| Компонент | Файл | Что делает |
|---|---|---|
| Датчик | `sensors/python/sensor.py` | своя модель уровня (режимы NORMAL / RISING / DANGER / FALLING с учебными целевыми уровнями), отправка раз в 2 с, буфер на время обрыва, переподключение, один экземпляр на устройство |
| Брокер | `apps/server/src/mqtt/broker.ts`, `broker-cli.ts` | Aedes (MIT, Node.js, без установки в систему); только 127.0.0.1; вход по паролю; права на топики |
| Подписчик | `apps/server/src/mqtt/subscriber.ts` | MQTT-клиент QORGAN: постоянная сессия, подписка QoS 1, автопереподключение, статус «online/offline» |
| Адаптер | `apps/server/src/mqtt/adapter.ts` | проверки MQTT-уровня и передача в `POST /api/telemetry` (через `app.inject`, как встроенный симулятор) |
| Протокол | `apps/server/src/mqtt/protocol.ts` | топики и схема сообщения (zod) |
| Устройства | таблица `devices` (миграция v3), `/api/admin/devices` | идентификатор, станция, хеш токена, состояние связи, защита от повторов |

**Почему Aedes, а не Mosquitto.** Mosquitto на ноутбуке не установлен, а для Windows он ставится системным установщиком. Aedes — MQTT-брокер на Node.js (MIT), запускается из папки проекта одной командой. Протокол стандартный: вместо Aedes можно поставить Mosquitto (см. §7).

## 2. Время: показание датчика и часы модели

Модуль риска T2 считает скорость в см/ч и рассчитан на почасовые данные. Датчик для демонстрации шлёт показание раз в 2 с. Поэтому, как и у встроенного симулятора («1 ч симуляции = 0,5 с»), в режиме датчиков **1 час модели = 2 с реального времени** (настройка прогона, `hourMs`):
- датчик ставит **реальное** время измерения; сервер проверяет его по своим часам (не из будущего > 30 с, не старше 5 мин);
- затем переводит в час модели: `час = round((время показания − начало прогона) / 2 с)`; в БД `measured_at` — время модели, `received_at` — реальное;
- поэтому скорость «18 см за показание» модель видит как 18 см/ч, а шум ±0,6 см — как «без изменений».

## 3. Источник данных: без смешивания

У каждого прогона один источник (`simulation.dataSource` в API и снимке):

| Режим | Как включить | Кто пишет данные |
|---|---|---|
| `INTERNAL_SIMULATION` | сценарий в «Симулятор» / «Демо за 2 минуты» | только встроенный симулятор |
| `EXTERNAL_SENSOR` | «Принимать данные от датчиков» («Симулятор» → «Внешние датчики») или `POST /api/simulation/external/start` | только устройства через MQTT; у симулятора нет таймера, пауза/шаг/вмешательства → 409 `EXTERNAL_RUN` |

- Пока идёт встроенная симуляция, показания датчика **не записываются** (`SOURCE_CONFLICT`, запись в журнале диагностики). Нет активного режима датчиков — `NO_EXTERNAL_RUN`.
- Переключение — через «Остановить»: история обоих режимов сохраняется как отдельные прогоны.
- Источник виден в интерфейсе: панель «Внешние датчики», строка прогона, пометка «внешний датчик (MQTT)» у измерения в карточке станции.
- Станции без своего датчика в режиме датчиков остаются «Нет данных» (симулятор их не заполняет). Станция ниже по течению может получить предупреждение «угроза сверху» — это обычная логика T2.

## 4. Протокол MQTT

| Топик | Кто публикует | QoS / retain | Содержимое |
|---|---|---|---|
| `qorgan/v1/sensors/{deviceId}/telemetry` | устройство | 1 / **нет** | показание (JSON ниже) |
| `qorgan/v1/sensors/{deviceId}/status` | устройство; брокер по завещанию | 1 / да | `online` / `offline` |
| `qorgan/v1/server/status` | QORGAN; брокер по завещанию | 1 / да | `online` (после подтверждения подписки) / `offline` |

Сообщение показания:
```json
{
  "v": 1,
  "deviceId": "PY-SENSOR-01",
  "stationId": "QRG-03",
  "type": "water_level",
  "value": 512.4,
  "unit": "cm",
  "timestamp": "2026-10-28T11:16:38.594Z",
  "seq": 15,
  "bootId": "3f2a9c1d7e44",
  "source": "PYTHON_SENSOR",
  "mode": "DANGER"
}
```
`seq` — номер показания в текущем запуске; `bootId` — случайный идентификатор запуска (после перезапуска датчика `seq` начинается с 1). Лишние поля отклоняются (`strict`).

### Доставка без потерь и без дублей
- **QoS 1** — брокер подтверждает приём (PUBACK). Подтверждение брокера не значит, что QORGAN получил сообщение, поэтому:
- датчик отправляет показания, **только когда QORGAN online** (`qorgan/v1/server/status`); иначе копит их в буфере (до 5 минут — старше сервер всё равно не примет) и отправляет по порядку, когда QORGAN снова online;
- QORGAN подключается с **постоянной сессией**: если он перезапускается, брокер хранит для него показания и отдаёт после возвращения;
- повторная доставка QoS 1 и повтор после переподключения: адаптер отбрасывает показание того же `bootId` с `seq` не новее последнего (`DUPLICATE`); вдобавок одно показание на час модели гарантирует `UNIQUE(run, station, parameter, measured_at)` в БД.
- Сохранённые брокером (retain) показания не пропускаются: брокер не даёт их опубликовать, адаптер отклоняет (`RETAINED`).

### Проверки (что отклоняется и куда пишется)
Брокер: анонимное подключение, неверный пароль, публикация не в свои топики, подписка на чужое, retained-показание (нарушителя брокер отключает). Адаптер (код в журнале диагностики `MQTT_*` — не чаще раза в 10 с на причину; **каждое** сообщение дополнительно учитывается в счётчике «устройство × прогон × итог», см. ниже): `BAD_JSON`, `BAD_FORMAT`, `SPOOFED_DEVICE` (deviceId в теле ≠ топику), `UNKNOWN_DEVICE`, `DEVICE_DISABLED`, `STATION_MISMATCH`, `FUTURE`, `STALE`, `RATE_LIMITED` (чаще раза в 500 мс по времени измерения или > 20 сообщений/с), `SOURCE_CONFLICT`, `NO_EXTERNAL_RUN`. Затем обычный приём телеметрии: диапазон, единица, станция устройства (`STATION_MISMATCH`), время. Предел прогона — 20 000 часов модели (защита от переполнения БД).

### Счётчики «принято / отклонено» и их причины
Каждое сообщение показания засчитывается в таблицу `device_run_results` (устройство, прогон, итог, количество). Отклонения, пришедшие, пока приём датчиков не включён, попадают в «прогон 0». Панель «Внешние датчики» показывает:
- **«Прогон №N: принято / отклонено»** — только текущий (или последний остановленный) прогон приёма датчиков;
- строку с причинами отклонений этого прогона (например, «приём датчиков не включён: 12») и числом повторов;
- **«за всё время»** — общие счётчики устройства (ничего не скрывается и не сбрасывается).

Типичные **нормальные** отклонения: `NO_EXTERNAL_RUN` — датчик уже передаёт, а приём ещё не включён; `SOURCE_CONFLICT` — идёт встроенная симуляция; `STALE` «до начала прогона» — показание из буфера, измеренное раньше старта нового прогона. Признак неполадки — `RATE_LIMITED`, `FUTURE`, `BAD_FORMAT` при обычной работе датчика.

## 5. Модель уровня воды датчика

Уровни — **учебные значения для демонстрации**, подобраны под учебные пороги станции Петропавловск в QORGAN (предупредительный 4,80 м, опасный 5,80 м). Это не официальные гидрологические нормы.

| Режим (клавиша) | Куда идёт уровень | Наибольший шаг за показание |
|---|---|---|
| NORMAL (N) | к начальному уровню `--initial` (3,20 м) | 4 см |
| RISING (R) | к пику подъёма `--rising-peak` (5,00 м) | 6 см |
| DANGER (D) | к опасному пику `--danger-peak` (6,50 м) | 18 см |
| FALLING (F) | к начальному уровню (быстрый спад) | 12 см |

- Шаг = четверть оставшегося расстояния до цели, но не больше скорости режима: подъём ровный, у цели плавно замедляется, **бесконечного роста нет** (раньше DANGER рос без ограничения — при ручной проверке 28.10 до 14,54 м, а NORMAL просто держал достигнутый уровень).
- Шум ±0,6 см детерминирован: одинаковые `--seed` (по умолчанию 1) и последовательность режимов дают одинаковый ряд.
- С интервалом 2 с: от нормы в DANGER уровень проходит 4,80 м примерно через 18 с, 5,80 м — через 30 с и выравнивается у 6,50 м примерно за минуту; F возвращает к 3,20 м примерно за минуту.
- Границы настраиваются: `--initial 300 --rising-peak 450 --danger-peak 600`; неверные сочетания (начальный ≥ пика, пик > 15 м) отклоняются при запуске.
- Второй экземпляр датчика с тем же устройством не запускается (блокировка файла `sensors/python/.sensor-<устройство>.lock`, её снимает система при завершении процесса) — два потока показаний не смешиваются.

## 6. Установка и запуск (Windows)

Нужно: Node.js 24 и Python 3 (python.org, при установке отметить «Add python.exe to PATH»). Docker не нужен.

**Одним щелчком:** `start-demo.bat` — проверяет Node.js и Python, при первом запуске ставит зависимости, запускает по порядку сервер (ждёт ответа `/api/health`), брокер (ждёт открытия порта), датчик и открывает сайт. Уже запущенные части не дублируются. `stop-demo.bat` закрывает только окна, запущенные BAT-файлами из этой папки (ищет их по командной строке, а не по заголовку окна — npm меняет заголовки), сначала мягко, через 3 с принудительно.

**По отдельности:**
1. **QORGAN** — `start-qorgan.bat` (сам выполнит `npm install`, `npm run setup`, сборку и запуск). Если порт уже занят QORGAN — второй сервер не запускается, открывается сайт.
2. **Брокер** — `start-broker.bat`. При самом первом запуске он ждёт, пока сервер создаст базу (до 5 минут). Строка «MQTT-брокер QORGAN работает» — готово.
3. На сайте: войти оператором → «Симулятор» → «Внешние датчики» → **«Подготовить чистое демо» → «Начать новый чистый прогон»**.
4. **Датчик** — `start-sensor.bat` (при первом запуске создаст окружение Python и установит `paho-mqtt`, нужен интернет один раз). Можно сразу `start-sensor.bat DANGER`.
5. В окне датчика — буква и Enter: **N** норма, **R** подъём, **D** опасный подъём, **F** спад, **Q** выход.

BAT-файлы — только латиница и окончания строк CRLF. Причина прежних ошибок (`'ова.' is not recognized`, `|| was unexpected at this time`, мгновенно закрывающееся окно): в рабочей папке файлы были в UTF-8 с LF-окончаниями, а `chcp 65001` переключал кодировку посреди чтения файла. cmd.exe читает .bat по частям по смещениям в байтах и начинал выполнять обрывки кириллических слов (ошибка воспроизведена на старом файле 29.10). Сейчас тексты BAT — английские; сообщения Node.js и Python по-прежнему русские (они выводятся через Unicode-API консоли и от кодовой страницы не зависят).

`npm run setup` сам добавляет в существующий `.env` недостающие ключи со случайными паролями (`MQTT_SERVICE_PASSWORD`, `SENSOR_TOKEN`); демо-устройство `PY-SENSOR-01` (станция QRG-03 «Петропавловск») создаётся при запуске сервера. Ничего редактировать руками не нужно.

Командами: `npm run mqtt:broker`; `sensors\python\.venv\Scripts\python.exe sensors\python\sensor.py --mode RISING --interval 2`; все параметры — `--help`.

## 8. Mosquitto вместо Aedes (не проверялось)

Те же правила в `mosquitto.conf`: `listener 1883 127.0.0.1`, `allow_anonymous false`, `password_file …`, ACL:
```
user qorgan-server
topic read qorgan/v1/sensors/#
topic write qorgan/v1/server/status
pattern write qorgan/v1/sensors/%u/telemetry
pattern write qorgan/v1/sensors/%u/status
pattern read qorgan/v1/server/status
```
Пароль устройства в password_file должен совпадать с его токеном. Запрет retained-показаний Mosquitto сам не обеспечивает — их отклонит адаптер QORGAN. В QORGAN указать `MQTT_URL=mqtt://127.0.0.1:1883`.

## 9. Ограничения

- Датчик программный; его модель уровня — учебная (не измерение реальной реки).
- Для показа время сжато: 1 показание = 1 час модели. В реальной системе датчик слал бы показание раз в 10–60 минут, и масштаб был бы 1:1.
- Брокер хранит сессии в памяти: при перезапуске брокера очередь для QORGAN теряется — эту ситуацию закрывает статус QORGAN (датчик ждёт «online»). Если датчик был без связи дольше 5 минут, старые показания отбрасываются.
- Брокер для публичного сервера в `docker-compose.yml` не включён: порт MQTT наружу не открываем. Для реальных датчиков в интернете нужен MQTT по TLS (8883) — не делалось.
- Один источник данных на прогон: смешанный режим «часть станций — симулятор, часть — датчики» сознательно не сделан.
- Mosquitto-вариант описан, но не проверялся.
