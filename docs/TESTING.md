# QORGAN — Стратегия тестирования

## 1. Уровни проверок

| Уровень | Инструмент | Что проверяем | Когда запускать |
|---|---|---|---|
| Модульные | Vitest | расчёт риска, модель волны, PRNG, правила предупреждений | после каждого изменения `packages/shared` и `server/simulator` |
| Интеграционные | Vitest + `fastify.inject()` + SQLite `:memory:` | API, транзакция тика, роли, дубли, перезапуск | после изменений сервера |
| Сборка | `npm run build` (tsc + vite) | типы, сборка фронтенда | перед каждым коммитом этапа |
| E2E ручные | чек-лист §5 | критические сценарии пользователя | после T4, T5, T9 и перед защитой |
| E2E авто (доп.) | Playwright (EX-006) | смоук Dashboard + старт сценария | только если останется время |

Команда: `npm test` (все), `npm test -w packages/shared` (только расчёты). Тесты не зависят от интернета и случайности (фиксированный seed).

## 2. Расчёт риска — TC-R (packages/shared/risk)

Общие параметры: W = 450, D = 550, N = 6, N_min = 3, ε = 0,5 см/ч, J_max = 50, H_high = 6 ч, H_med = 24 ч, H_up = 72 ч. Время t — часы, шаг 1.

| ID | Уровни h(t=0..n) | Ожидается |
|---|---|---|
| TC-R01 | 300, 302 | n=2 < 3 → rate=null, trend UNKNOWN, ETA null, risk LOW, причины [INSUFFICIENT_DATA], доверие LOW |
| TC-R02 | 560 | risk HIGH, ETA 0, причины включают LEVEL_ABOVE_DANGER и INSUFFICIENT_DATA |
| TC-R03 | 300 ×6 | rate 0, STABLE, ETA null, LOW |
| TC-R04 | 400, 410, 420, 430, 440, 450 | rate 10, RISING, ETA = 10 ч, risk MEDIUM (LEVEL_ABOVE_WARNING, ETA_DANGER_WITHIN{hours:10}) |
| TC-R05 | 420, 440, 460, 480, 500, 520 | rate 20, ETA = 1,5 ч, risk HIGH |
| TC-R06 | 540, 550, 560, 570, 580, 590 | ETA 0 («превышен»), HIGH, LEVEL_ABOVE_DANGER |
| TC-R07 | 500, 490, 480, 470, 460, 450 | rate −10, FALLING, ETA null, MEDIUM (по уровню, h = W) |
| TC-R08 | 440, 430, 420, 410, 400, 390 | FALLING, LOW |
| TC-R09 | 300, 302, 304, **420**, 308, 310 | точка t=3 исключена (SPIKE_IGNORED); rate ровно 2,0; ETA = 120 ч > 24 → LOW |
| TC-R10 | 300, 302, 304, 306, 308, **600** | последняя точка — SPIKE_UNCONFIRMED; расчёт по h = 308 → LOW, доверие LOW |
| TC-R11 | 302, 304, 306, 308, 600, 605 | скачок устойчив → SUDDEN_JUMP, h = 605 ≥ D → HIGH |
| TC-R12 | 300, 300.2, 300.4, 300.6, 300.8, 301 | rate 0,2 < ε → STABLE, LOW |
| TC-R13 | 300 ×6, верхняя станция HIGH, τ = 51 ч | MEDIUM, причина UPSTREAM_WAVE{station, hours:51}; при τ = 80 ч (> H_up) или верхней MEDIUM — LOW |
| TC-R14 | ряд с шумом ±3 см вокруг роста 10 см/ч | диапазон ETA содержит точечную оценку: eta_low ≤ eta ≤ eta_high; при v − SE ≤ ε правая граница null |

Плюс свойства: результат не зависит от порядка входного массива (сортировка по tick); пустое окно не бросает исключение (LOW + INSUFFICIENT_DATA); W ≥ D отклоняется валидацией.

## 3. Симулятор — TC-S

| ID | Проверка |
|---|---|
| TC-S01 | Один и тот же scenario+params+seed → идентичные ряды по всем станциям (воспроизводимость) |
| TC-S02 | Другой seed → другой шум, та же форма волны (разница ≤ 2σ) |
| TC-S03 | При σ = 0 и a_d = 0 начало подъёма на QRG-02 ровно через τ2 = 51 тик после QRG-01; на QRG-03 — через 102; на QRG-04 — через 119 |
| TC-S04 | Сценарии дают ожидаемые пики (ARCHITECTURE §7, допуск ±5 см) и уровни риска |
| TC-S05 | Повторная обработка того же тика не создаёт дублей (UNIQUE run_id+station_id+tick) |
| TC-S06 | pause останавливает тики; resume продолжает с того же номера; step добавляет ровно 1 тик |
| TC-S07 | Перезапуск сервера в RUNNING → PAUSED на последнем сохранённом тике, данных не потеряно |
| TC-S08 | Недопустимые переходы (start при RUNNING, resume при IDLE) → 409 |

## 4. Предупреждения — TC-A, API — TC-P, БД — TC-D, локализация — TC-I

| ID | Проверка |
|---|---|
| TC-A01 | LOW → MEDIUM создаёт ровно 1 предупреждение (OPENED) |
| TC-A02 | MEDIUM 10 тиков подряд → по-прежнему 1 предупреждение, обновляется last_tick |
| TC-A03 | MEDIUM → HIGH: то же предупреждение, событие ESCALATED |
| TC-A04 | ack → ACKNOWLEDGED, событие с user_id и комментарием; повторный ack → 409 |
| TC-A05 | 3 тика LOW подряд → RESOLVED_AUTO; 2 тика LOW + MEDIUM → не закрывается |
| TC-A06 | После закрытия новый подъём → новое предупреждение |
| TC-P01 | Снимок WS и `GET /api/state` после одного тика совпадают (runId, tick, уровни, риск) |
| TC-P02 | История измерений возвращает точки в порядке tick, фильтры from/to работают |
| TC-P03 | История риска содержит пороги, действовавшие на тот момент |
| TC-P04 | Валидация: неверный stationId/levelCm → 400 |
| TC-P05 | Команды без входа → 401; operator в admin-API → 403 |
| TC-P06 | Изменение порогов админом действует со следующего тика, запись в audit_log |
| TC-P07 | Неверный пароль → 401, пароль в БД хранится только как хеш |
| TC-D01 | Миграции на пустой БД применяются; повторный запуск ничего не ломает |
| TC-D02 | Seed создаёт 4 станции в правильном порядке и с W < D |
| TC-D03 | backup создаёт читаемый файл БД с теми же данными |
| TC-I01 | Файлы kk/ru/en содержат одинаковый набор ключей, без пустых значений |
| TC-I02 | Каждый ReasonCode и статус имеет перевод на 3 языках |

## 6. Правила

- Не писать «проверено», если тест не запускался. В отчёте — команда и результат.
- Падающий тест не удаляют и не ослабляют без объяснения пользователю.
- Ошибки, найденные вручную, сначала воспроизводятся тестом (если реально за ≤ 15 мин), потом исправляются.
