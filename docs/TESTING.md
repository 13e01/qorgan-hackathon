# QORGAN — Стратегия тестирования

Критерии ТЗ §9, которые закрывают тесты: «прогнозирование — корректность демонстрации» (TC-R, TC-S), «надёжность — проверка данных, роли, обработка ошибок» (TC-T, TC-P).

## 1. Уровни проверок

| Уровень | Инструмент | Что проверяем | Когда |
|---|---|---|---|
| Модульные | Vitest | модуль риска, генерация сценариев, хеш-шум, правила предупреждений | после каждого изменения `packages/shared`, `apps/simulator` |
| Интеграционные | Vitest + `fastify.inject()` + SQLite `:memory:` | телеметрия, транзакция, роли, CRUD, дубли | после изменений сервера |
| Сборка | `npm run build` | типы, сборка фронтенда | перед каждым коммитом этапа |
| Ручные E2E | чек-лист §6 | пользовательские сценарии | после T4–T6, T9 и перед защитой |
| Авто-E2E (доп.) | Playwright (~150 МБ загрузки, по согласованию) | смоук | только при запасе времени |

`npm test` — всё; `npm test -w packages/shared` — только расчёты. Тесты не зависят от интернета и случайности.

## 3. Симулятор — TC-S

| ID | Проверка |
|---|---|
| TC-S01 | Одинаковые scenario + params + seed → идентичные пакеты (воспроизводимость, ТЗ §9) |
| TC-S02 | Другой seed → другой шум, та же форма (разница ≤ 2σ) |
| TC-S03 | При σ = 0, a_d = 0 подъём у QRG-02 начинается через 51 тик после QRG-01, у QRG-03 — через 102, у QRG-04 — через 119 |
| TC-S04 | Пики сценариев совпадают с ARCHITECTURE §6.4 (±5 см); SC-NORMAL — все LOW; SC-MODERATE — максимум MEDIUM; SC-SEVERE — все станции достигают HIGH, QRG-01 получает MEDIUM раньше начала роста уровня |
| TC-S05 | Генерация тика k не зависит от того, генерировались ли тики до него (хеш-шум) |
| TC-S06 | pause останавливает отправку; resume продолжает с того же тика; step — ровно 1 тик |
| TC-S07 | Перезапуск симулятора → продолжает с `last_tick + 1`; перезапуск backend в RUNNING → PAUSED |
| TC-S08 | Недопустимые команды (start при RUNNING, resume при IDLE) → 409 |
| TC-S09 | SC-FAULTS: ни одного ложного предупреждения; в журнале есть SPIKE, GAP, REJECTED_RANGE, LATE |

## 4. Приём телеметрии — TC-T

| ID | Проверка |
|---|---|
| TC-T01 | Корректный пакет → сохранены все 5 полей ТЗ §5.2 + `received_at`; ответ `accepted = n` |
| TC-T02 | Неверный/отсутствующий токен → 401; станция `disabled` → 409 |
| TC-T03 | Неизвестный параметр или не из набора станции → отклонено `UNKNOWN_PARAM` |
| TC-T04 | Неверная единица → `REJECTED_UNIT`; значение вне диапазона, NaN, −999 → `REJECTED_RANGE`; запись в `device_log` |
| TC-T05 | Повтор того же пакета → `duplicates = n`, в БД нет дублей |
| TC-T06 | `measuredAt` позже модельного времени → отклонено; раньше последнего → сохранено с `quality = 'late'` |
| TC-T07 | Нет сообщений > 3 × tick_ms → STALE, > 10 × → OFFLINE; восстановление → ONLINE и `RECONNECTED` |
| TC-T08 | Ошибка внутри транзакции → ничего из пакета не сохранено, ответ 500, симулятор повторяет |

## 5. Предупреждения, API, БД, языки

| ID | Проверка |
|---|---|
| TC-A01 | LOW → MEDIUM создаёт ровно 1 предупреждение со временем, станцией, типом ЧС, уровнем, причиной |
| TC-A02 | MEDIUM 10 пакетов подряд → по-прежнему 1, обновляется `last_tick` |
| TC-A03 | MEDIUM → HIGH: то же предупреждение, `ESCALATED`; trigger `DANGER_LEVEL` при h ≥ D, иначе `FORECAST` |
| TC-A04 | «Просмотрено» и «Обработано» сохраняют автора и комментарий; повтор → 409; гость → 401 |
| TC-A05 | 3 пакета LOW подряд → `CLEARED`, `is_active = 0`; 2 LOW + MEDIUM → условие не снимается |
| TC-A06 | Ухудшение после `CLEARED` → новое предупреждение |
| TC-A07 | Параллельные пакеты одной станции не создают двух активных предупреждений (уникальный индекс) |
| TC-P01 | Снимок WS и `GET /api/state` после пакета совпадают |
| TC-P02 | История измерений по параметру в порядке времени; фильтры работают; гость получает только 24 ч |
| TC-P03 | История риска хранит пороги и версию `risk_config` того момента |
| TC-P04 | Неверное тело любого запроса → 400 с понятным кодом, сервер не падает |
| TC-P05 | Команды без входа → 401; оператор в `/api/admin/*` → 403 |
| TC-P06 | Изменение порогов/коэффициентов действует со следующего пакета; запись в `audit_log` |
| TC-P07 | Неверный пароль → 401; в БД только scrypt-хеш |
| TC-P08 | Матрица доступа ARCHITECTURE §10 соблюдается для каждого маршрута (табличный тест) |
| TC-P09 | CRUD станций: создание с W ≥ D → 400; DELETE переводит в `disabled`, история сохраняется |
| TC-P10 | CRUD пользователей: нельзя удалить/понизить последнего активного админа; деактивированный не входит |
| TC-D01 | Миграции применяются к пустой БД и повторно ничего не ломают |
| TC-D02 | Seed: 4 станции в правильном порядке, W < D, пользователи с хешами |
| TC-D03 | Резервная копия открывается и содержит те же данные |
| TC-I01 | kk/ru/en содержат одинаковые ключи без пустых значений |
| TC-I02 | Каждый код причины, статуса и ошибки переведён на 3 языка |

## 7. Правила

- Нельзя писать «проверено», если проверка не запускалась; в отчёте — команда и результат.
- Падающий тест не удаляют и не ослабляют без объяснения пользователю.
- Ошибку, найденную вручную, сначала воспроизводят тестом (если это занимает ≤ 15 мин), потом исправляют.
