## 1. Общая структура

Цепочка из ТЗ §6 «датчик/симулятор → API → backend → БД → оценка риска → предупреждения → веб-интерфейс и карта» реализуется буквально:

```
┌──────────────────────────┐   HTTP POST /api/telemetry      ┌──────────────────────────────────────────────┐
│ Симулятор (apps/simulator)│ ── X-Device-Token, пакет за тик ─►│ Backend Fastify (apps/server)                │
│ отдельный Node-процесс    │                                   │  ingest/   проверка допустимости, дедупликация│
│ сценарии, модель волны,   │ ◄── GET /api/simulation/control ──│  risk/     модуль оценки риска (packages/shared)│
│ детерминированный шум     │     (команды: старт/пауза/сброс)  │  alerts/   предупреждения и журнал          │
└──────────────────────────┘                                   │  admin/    CRUD станций, пользователей, порогов│
   (вместо него можно подключить ESP32 — тот же API)            │  realtime/ WebSocket-рассылка снимков        │
                                                                │  db/       node:sqlite, миграции, seed, backup│
                                                                └───────────────┬──────────────────▲───────────┘
                                                                     SQLite файл │                  │ REST + WS
                                                                  data/qorgan.db ▼                  │
                                                                                     ┌──────────────┴─────────┐
                                                                                     │ Веб-интерфейс (apps/web)│
                                                                                     │ React, карта MapLibre,  │
                                                                                     │ графики, kk/ru/en       │
                                                                                     └─────────────────────────┘
```

Каталоги (создаются в Phase 1):

```
apps/server/      — backend API
apps/simulator/   — источник телеметрии (отдельный процесс; общается с backend только по HTTP)
apps/web/         — frontend
packages/shared/  — типы, модуль оценки риска (чистые функции), определения сценариев и параметров
data/             — файл БД и резервные копии (в .gitignore)
docs/             — документация, презентация
```

`npm start` (и `start-demo.bat`) запускает два процесса: backend (он же отдаёт собранный фронтенд на :3000) и симулятор.

## 2. Ответственность компонентов

| Компонент | Отвечает за | НЕ отвечает за |
|---|---|---|

| `server/alerts` | Создание/повышение/снятие условия, отметки «просмотрено»/«обработано», история | Отправку SMS/почты |
| `server/admin` | CRUD станций, их параметров и порогов, коэффициентов риска, пользователей; состояние источников; аудит | — |
| `server/realtime` | Рассылка снимка после каждого обработанного пакета; снимок при подключении | — |
| `web` | Отображение, команды, вход, языки, адаптивная вёрстка | Пересчёт риска |

**Правило согласованности:** риск считается только на backend, один раз на обработанный пакет, в той же транзакции, что и запись измерений; результат сохраняется. Карта, карточка, графики, прогноз и предупреждения показывают данные одного снимка (`runId + tick`).

## 3. Выбранная ЧС и показатели [ТЗ §1, §3]

Тип ЧС: **паводки и подтопления** (весеннее половодье на р. Есиль, СКО).

| Параметр | Код | Единица | Почему связан с угрозой | Допустимый диапазон* | Макс. скачок за тик* |
|---|---|---|---|---|---|
| Уровень воды | `water_level` | см (над учебным нулём поста) | Прямой показатель затопления; его рост и скорость роста — основа прогноза | 0…1500 | 50 |
| Интенсивность осадков | `precipitation` | мм/ч | Дождь на снег/мёрзлую почву быстро увеличивает сток в реку | 0…100 | — |
| Температура воздуха | `air_temp` | °C | Положительная температура весной → снеготаяние → приток воды | −50…+45 | 10 |

\* учебные значения. Скорость роста уровня — **вычисляемый** показатель, а не отдельный датчик.

## 6. Симулятор

### 6.1 Управление и состояния
Симулятор — отдельный процесс. Раз в 500 мс он читает `GET /api/simulation/control` (желаемое состояние, которое оператор меняет через UI) и действует:

```
         start(scenario, seed, params)           pause
  IDLE ─────────────────────────────► RUNNING ◄──────► PAUSED
   ▲                                     │     resume     │  step (1 тик)
   │      reset (новый run_id)           │ конец сценария  │
   └─────────────────────────────────────┴─► FINISHED ◄───┘   (reset из любого состояния → IDLE)
```

- Недопустимые команды → HTTP 409 (например, `start` при RUNNING).
- Частота настраивается: `tick_ms` 250–5000 мс [ТЗ §5.2]. 1 тик = 1 час модельного времени, `measured_at = sim_start + tick·1 ч`.
- **Перезапуск симулятора:** он запрашивает `last_tick` прогона и продолжает с `last_tick + 1`. **Перезапуск backend:** RUNNING переводится в PAUSED.
- Повтор отправки при ошибке сети: тот же пакет (те же `measured_at`) — backend отвечает «дубликат», данные не удваиваются.

### 6.2 Детерминизм
Шум не хранит состояние: `noise = σ · (2·u − 1)`, где `u = hash(seed, stationCode, parameter, tick) / 2³²` (хеш mulberry32/xmur3). Любой тик можно пересчитать заново, одинаковые `scenario + params + seed` ⇒ одинаковые ряды.

### 6.3 Модель паводковой волны (учебная, не гидродинамика)
```
Исток (станция без upstream):   h(t) = base + A·pulse(t − t0) + a_d·sin(2πt/24) + noise
pulse — трапеция: рост T_rise ч до 1, плато T_peak ч, спад T_fall ч до 0
Нижние станции:                 h_k(t) = base_k + α_k·(clean_{k−1}(t − τ_k) − base_{k−1}) + L_k(t) + noise_k
                                clean_{k−1} — уровень верхней станции без шума (шум не копится по цепочке)
                                при t − τ_k < 0 — базовый уровень
Станции без upstream и не исток сценария — обычный режим (base + суточное колебание + шум).
```
Учебные коэффициенты: a_d = 3 см, σ = 2 см, α₂ = 0.95, α₃ = 1.05, α₄ = 0.9.

Осадки и температура задаются сценарием как функции времени для каждой станции (дождь — локально в верховьях; температура — общая по региону ± 0,5 °C).

### 6.4 Сценарии [ТЗ §5.2: минимум «норма» и «опасное событие»]

| ID | Название | Уровень (A; t0/T_rise/T_peak/T_fall, ч) | Осадки | Температура | Ожидаемый результат |
|---|---|---|---|---|---|
| SC-NORMAL | Обычный режим | A = 0 | 0, иногда до 0,5 мм/ч | −3 °C ± 2 (суточный ход) | все станции LOW, предупреждений нет |
| SC-MODERATE | Умеренный паводок | 180; 10/24/12/48 | QRG-01: 2 мм/ч, тики 4–9 (12 мм) | от −2 до +1 °C за 24 ч, далее +1 | пики ≈480/451/500/422 см → все станции по очереди MEDIUM, HIGH не возникает |
| SC-SEVERE | Сильное весеннее половодье | 300; 10/18/24/60; L₃ = +40 см на пике | QRG-01: 4 мм/ч, тики 4–9 (24 мм) | от −4 до +8 °C за 24 ч, далее +8 | ранний MEDIUM у QRG-01 по осадкам и потеплению до роста уровня; пики ≈600/565/659/565 см → все станции по очереди HIGH |
| SC-FAULTS | Сбои данных | как SC-MODERATE + сбои | как SC-MODERATE | как SC-MODERATE | выброс +150 см у QRG-02 (тик 30), пропуск QRG-03 (тики 40–45), значение −999 у QRG-04 (тик 50), запоздавший пакет QRG-01 (тик 60 доставлен на тике 63) — ни одной ложной тревоги, всё в журнале диагностики |

Оператор может также вручную включить сбой на станции (`faults` в `sim_control`) или ввести ручное измерение.

Длительность SC-SEVERE ≈ 10 + 102 (волна у истока) + 119 (добегание до QRG-04) ≈ 231 тик; при `tick_ms = 500` ≈ 2 мин.

## 7. Приём телеметрии [ТЗ §5.3]

`POST /api/telemetry`, заголовок `X-Device-Token`, тело:
```json
{ "runId": 3, "tick": 41, "records": [
  { "stationCode": "QRG-01", "parameter": "water_level", "value": 512.4, "unit": "cm", "measuredAt": "2026-04-02T17:00:00Z" } ] }
```
Проверки по каждой записи (непрошедшие не сохраняются, а пишутся в `device_log`, ответ перечисляет причины):
1. токен соответствует станции; станция `active` (иначе 401/409);
2. параметр входит в набор показателей станции; единица совпадает со справочником;
3. значение — конечное число в допустимом диапазоне (`REJECTED_RANGE`);
4. `measuredAt` — корректная дата не позже текущего модельного времени прогона;
5. дубликат (`UNIQUE`) → `DUPLICATE`, ответ 200 (идемпотентность);
6. `measuredAt` раньше последнего принятого → сохраняется с `quality='late'`, код `LATE`;
7. скачок больше `max_step` → сохраняется с `quality='suspect'`, решение принимает модуль риска (§8 шаг 2).

Ответ: `{ accepted, duplicates, rejected: [{ index, code }] }`. Затем в **той же транзакции**: пересчёт риска для затронутых станций (сверху вниз по течению) → обновление предупреждений → снимок в WebSocket.

**Состояние источников** [ТЗ §5.7]: по `last_message_at` (реальное время): `ONLINE` — не дольше 3 × `tick_ms`, `STALE` — до 10 × `tick_ms`, `OFFLINE` — дольше. Переходы пишутся в `device_log`. При STALE/OFFLINE карточка показывает «данные устарели», риск — последний рассчитанный с пометкой времени.

## 8. Модуль оценки риска [ТЗ §5.4]

**Базовый вариант ТЗ:** прозрачные правила + весовые коэффициенты + оценка тренда. Это **не ML и не научно подтверждённый прогноз**; в интерфейсе постоянно видна пометка «Учебная модель, демонстрационные данные».

Параметры (учебные, хранятся в `risk_config`, меняет admin): `N = 6`, `N_min = 3`, `ε = 0.5 см/ч`, `J_max = 50 см`, горизонт прогноза `H_f = 3 ч`, `H_high = 6 ч`, `H_med = 24 ч`, `H_up = 72 ч`, `P1 = 10 мм`, `P2 = 20 мм` (осадки за 6 ч), `T_melt = +2 °C` (средняя за 24 ч).

### Шаги для станции
1. **Окно уровня:** последние N измерений `water_level` (по `measured_at`).
2. **Выбросы:** точка j (не последняя) — одиночный выброс, если `|h_j − h_{j−1}| > J_max` и `|h_{j+1} − h_{j−1}| ≤ J_max/2` → исключается (`SPIKE_IGNORED`). Последняя точка со скачком `> J_max` — неподтверждённый скачок: расчёт по предыдущей точке, доверие LOW (`SPIKE_UNCONFIRMED`); если следующий тик скачок подтвердил — точка принимается (`SUDDEN_JUMP`).
3. **Скорость** — наклон МНК: `v = Σ(t−t̄)(h−h̄) / Σ(t−t̄)²` (см/ч). Если точек < N_min → `v = null`, тренд UNKNOWN (`INSUFFICIENT_DATA`).
4. **Тренд:** RISING при v > ε; FALLING при v < −ε; иначе STABLE.
5. **Прогноз на горизонт H_f = 3 ч:** `h₃ = h + 3·v`, диапазон `h + 3·(v ± SE)`, где `SE = sqrt(Σres²/(n−2) / Σ(t−t̄)²)`.
6. **ETA до опасного порога D:** `h ≥ D` → 0; RISING → `(D − h)/v`, диапазон `[(D−h)/(v+SE), (D−h)/(v−SE)]` (правая граница «не ограничена», если `v − SE ≤ ε`); иначе null.
7. **Доверие:** HIGH — n = N и SE ≤ 0.25·|v|; MEDIUM — n ≥ N_min; LOW — n < N_min, неподтверждённый скачок или данные устарели.
8. **Факторы и баллы** (весовые коэффициенты по умолчанию; каждый фактор — причина с параметрами):

| Фактор | Условие → баллы | Код причины |
|---|---|---|
| F1 Уровень | h ≥ D → 4; h ≥ W → 2; иначе 0 | `LEVEL_ABOVE_DANGER` / `LEVEL_ABOVE_WARNING` |
| F2 Тенденция | RISING и ETA ≤ H_high → 3; RISING и ETA ≤ H_med → 2; RISING → 1; иначе 0 | `ETA_DANGER_WITHIN{hours}` / `RISING{rate}` |
| F3 Осадки | сумма за 6 ч ≥ P2 → 2; ≥ P1 → 1 | `HEAVY_RAIN{mm}` |
| F4 Температура | средняя за 24 ч ≥ T_melt → 1 | `SNOWMELT{temp}` |
| F5 Волна сверху | верхняя станция HIGH и τ ≤ H_up → 2; MEDIUM и τ ≤ H_up → 1 | `UPSTREAM_WAVE{station, hours}` |

Нет данных по параметру → фактор 0, причина `NO_DATA{parameter}`.

9. **Категория:** HIGH, если `h ≥ D` или `score ≥ 5`; MEDIUM, если `score ≥ 2`; иначе LOW.
10. **Результат:** категория, балл, факторы с вкладом, тренд, скорость, прогноз на 3 ч с диапазоном, ETA с диапазоном, доверие, пороги и версия `risk_config`, по которым считали.

## 9. Предупреждения [ТЗ §5.6]

- Срабатывание: риск станции стал MEDIUM/HIGH и активного предупреждения нет → `OPENED`. Поля: время, станция, тип ЧС (`flood`), уровень (`severity`), причина (`trigger`: `DANGER_LEVEL` при h ≥ D, иначе `FORECAST` — «ухудшение прогноза»), список факторов.
- MEDIUM → HIGH: то же предупреждение, `ESCALATED`; HIGH → MEDIUM — `DEESCALATED`.
- Риск LOW 3 обработки подряд → условие снято (`CLEARED`, `is_active = 0`). Новое ухудшение после этого → новое предупреждение.
- Оператор: «Просмотрено» (NEW → VIEWED), «Обработано» (→ RESOLVED, комментарий). Отметки не зависят от `is_active`: тревогу можно обработать, пока условие действует.
- Дубли исключены уникальным индексом «одно активное предупреждение на станцию в прогоне» и транзакцией.

Вход: `scrypt` из `node:crypto`; сессия хранится в таблице `sessions`, браузер получает подписанную httpOnly-cookie `qorgan_sid` (`@fastify/cookie`, секрет из `.env`), срок 12 ч. Демо-учётки создаёт seed (пароли из `.env`; в git только `.env.example`). Регистрации нет — пользователей создаёт админ. Последнего активного админа удалить/понизить нельзя.

## 12. Обновление в реальном времени

- `GET /ws` (WebSocket, `@fastify/websocket`), только сервер → клиент; команды — REST.
- Сообщения: `snapshot` (при подключении и после каждой обработки пакета/команды), `alert_event`, `station_updated`, `source_status`.
- Снимок содержит `runId + tick`; клиент игнорирует более старые. Переподключение 1 → 2 → 5 с, индикатор «Связь потеряна».
- Графики: история через REST, затем дополняются точками из снимков.

## 13. Интерфейс

Разделы: **Dashboard** (карта + сводка + последние предупреждения), **Stations** (список и карточка), **Simulation**, **Analytics**, **Alerts**, **Admin**, **Login**.

- Тёмная тема ситуационного центра; цвета риска дублируются текстом/иконкой (не только цветом).
- **Адаптивность** [ТЗ §7, §9]: ≥1280 px — карта + боковая панель; 768–1279 — панель под картой; < 768 (телефон) — нижняя навигация, карточка станции на весь экран, таблицы → карточки.
- Карта: MapLibre + стиль OpenFreeMap `dark` (без ключа); офлайн-запас — встроенный GeoJSON реки и станций из OSM. **Зона риска** (бонус §8): участки русла между станциями окрашиваются по риску нижней станции, вокруг станции в HIGH — пульсирующий круг.
- Постоянный бейдж «ДЕМО-ДАННЫЕ · учебная модель» [ТЗ §5.4, §11].

## 14. Локализация (бонус [ТЗ §8])

`i18next` + `react-i18next`, файлы `apps/web/src/i18n/{kk,ru,en}.json`; по умолчанию ru, выбор в localStorage. Сервер отдаёт только коды (причины, статусы, ошибки), переводит фронтенд. Числа и даты — `Intl` с `kk-KZ`/`ru-RU`/`en-GB`. Тест полноты ключей. Казахский текст проверяет носитель языка.

## 15. Надёжность, резервное копирование, восстановление [ТЗ §9 «Надёжность»]

- Проверка данных: §7 (телеметрия), zod-схемы на всех входах API, CHECK-ограничения в БД.
- Ошибки: единый обработчик Fastify → понятный код; фронтенд показывает сообщение, а не «белый экран» (error boundary).
- Каждая обработка пакета — одна транзакция; при сбое — откат, симулятор повторяет пакет.
- Резервная копия: `VACUUM INTO data/backups/qorgan-ГГГГММДД-ЧЧММ.db` (`npm run db:backup`, кнопка в Admin). Полный сброс: `npm run db:reset`.
- Код: коммит после этапа, тег `checkpoint-*` перед рискованными изменениями; `git push` — только с разрешения.

## 16. Запуск

- Разработка: `npm install`, затем `npm run dev` (backend :3000, Vite :5173 с прокси, симулятор).
- Демо: `npm run build`, затем `npm start` или `start-demo.bat` → http://localhost:3000.
- Симулятор отдельно (для показа независимости источника): `npm run simulator`.

## 17. Источники данных, допущения, ограничения [ТЗ §10]

- **Источники:** геометрия реки и населённых пунктов — OpenStreetMap (ODbL); подложка — OpenFreeMap. Показания — **только симулятор**.
- **Допущения:** задержка волны пропорциональна расстоянию (3 км/ч); линейное ослабление/усиление волны; дождь и потепление увеличивают риск по фиксированным баллам; пороги W/D выбраны учебно.
- **Ограничения точности:** линейная экстраполяция на 3 ч не учитывает нелинейную динамику, лёд, дамбы, водохранилище, приток притоков; коэффициенты не откалиброваны на реальных данных; качество прогноза не измерено. Система — учебный прототип, не сертифицированная система оповещения [ТЗ §11].
