# QORGAN — Архитектура

> Версия 3 (2026-10-28, T3): симулятор, модель времени, приём телеметрии. Версия 2 — сверка с официальным ТЗ ([docs/tz/TZ-TRANSCRIPT.md](tz/TZ-TRANSCRIPT.md)).
> Ссылки вида `[ТЗ §5.4]` — на пункт ТЗ. Все пороги, задержки, коэффициенты и уровни — **учебные значения**, не официальные данные.

## 1. Общая структура

Цепочка из ТЗ §6 «датчик/симулятор → API → backend → БД → оценка риска → предупреждения → веб-интерфейс и карта»:

```
┌─────────────────────────────── Backend Fastify (apps/server), один процесс ────────────────────────────────┐
│                                                                                                              │
│  simulation/runner ── пакет за тик ──► POST /api/telemetry ──► telemetry/ingest ──► SQLite (data/qorgan.db) │
│  (таймер, команды,     X-Device-Token   (тот же HTTP-маршрут,   проверка, запись,      ▲                      │
│   виртуальные часы)    симулятора       что и для устройств)    часы прогона, риск ────┘ risk_assessments     │
│        ▲                                       ▲                       │                                      │
│        │ REST /api/simulation/* (оператор)     │ ESP32 / внешний       ▼                                      │
│        │                                       │ источник по сети   risk/service → shared/risk (T2)           │
│  realtime/hub ── WebSocket /ws: снимок после каждого пакета и команды ───────────────────────────────────────┤
└─────────────────────────────────────────────────────────────────────────────────────────────────────────────┘
                     ▲ REST + WS
           Веб-интерфейс (apps/web, T4): React, MapLibre, графики, kk/ru/en
```

Встроенный симулятор передаёт данные **через HTTP-маршрут `POST /api/telemetry`** (Fastify `inject`, в том же процессе — без сети): он проходит ту же аутентификацию, проверку и транзакцию, что и внешнее устройство. Почему не отдельный процесс, как планировалось в ADR-005, — см. ADR-017.

Каталоги:

```
apps/server/      — backend API, симулятор (src/simulation), приём телеметрии (src/telemetry), демо (src/demo)
apps/web/         — frontend (T4)
packages/shared/  — типы, модуль оценки риска, генератор волны и сценарии (чистые функции)
data/             — файл БД, резервные копии, демо-база (в .gitignore)
docs/             — документация, презентация
```

| `server/simulation` | Исполнитель: команды оператора, таймер тиков, виртуальные часы прогона, доставка пакетов в `POST /api/telemetry`, восстановление после перезапуска | Риск |

| `server/alerts` | Создание/повышение/снятие условия, отметки «просмотрено»/«обработано», история | Отправку SMS/почты |
| `server/admin` | CRUD станций, их параметров и порогов, коэффициентов риска, пользователей; состояние источников; аудит | — |
| `server/realtime` | Рассылка снимка после каждого обработанного пакета; снимок при подключении | — |
| `web` | Отображение, команды, вход, языки, адаптивная вёрстка | Пересчёт риска |

**Правило согласованности:** риск считается только на backend, один раз на обработанный пакет, в той же транзакции, что и запись измерений; результат сохраняется. Карта, карточка, графики, прогноз и предупреждения показывают данные одного снимка (`runId + tick`).

## 3. Выбранная ЧС и показатели [ТЗ §1, §3]

Тип ЧС: **паводки и подтопления** (весеннее половодье на р. Есиль, СКО).

| Параметр | Код | Единица | Почему связан с угрозой | Допустимый диапазон* | Макс. скачок за тик* |
|---|---|---|---|---|---|
| Уровень воды | `water_level` | см (над учебным нулём поста) | Прямой показатель затопления; его рост и скорость роста — основа прогноза | 0…1500 | 50 |
| Интенсивность осадков | `precipitation` | мм/ч | Дождь на снег/мёрзлую почву быстро увеличивает сток в реку | 0…100 | — |
| Температура воздуха | `air_temp` | °C | Положительная температура весной → снеготаяние → приток воды | −50…+45 | 10 |

\* учебные значения. Скорость роста уровня — **вычисляемый** показатель, а не отдельный датчик.

Запись телеметрии содержит всё, что требует ТЗ §5.2: станция, время измерения, параметр, значение, единица.

Миграции: v1 — исходная схема (T1); v2 — симулятор (T3): у станций `response_hours` (сглаживание волны), статус и часы у `sim_runs`, `sim_interventions`, `risk_assessments.assessment_json`, индекс `measurements(run_id, tick)`. Миграция только добавляет данные и столбцы; `sim_control` (одна служебная строка) пересоздаётся. Существующие прогоны получают статус COMPLETED.

## 6. Симулятор (T3)

Код: генератор и сценарии — `packages/shared/src/simulation/`; исполнитель, команды и хранение — `apps/server/src/simulation/`; приём — `apps/server/src/telemetry/ingest.ts`.

### 6.0 Модель времени
Время хранится в UTC (ISO 8601); часовой пояс Казахстана (UTC+5, `Asia/Almaty`) применяется только при отображении.

| Время | Где | Откуда берётся |
|---|---|---|
| **Реальное** | `received_at` измерения, `computedAt` оценки, `context.realTime`, `started_at` / `stopped_at` / `finished_at` прогона, `last_message_at` станции, журналы | единственный источник `now()` приложения (в тестах — управляемые часы) |
| **Виртуальное** (модельное) | `measured_at` измерения, `asOf` оценки, `context.virtualTime`, `virtualTime` прогона | только часы прогона: `sim_start + current_tick × step_minutes` (шаг 60 мин) |
| **Скорость** | `sim_runs.tick_ms` | сколько реальных мс длится один виртуальный час; ускорение = 3 600 000 / tick_ms (при 1000 мс — ×3600) |

- Виртуальное время двигается **только тиками**. Пауза и остановка снимают таймер — виртуальные часы стоят, сколько бы ни шло реальное время.
- Скорость меняет только паузу между тиками. Задержка волны 51 ч (Сергеевка → Явленка) — это 51 **виртуальный** час: при 1000 мс на тик это 51 реальная секунда, при 100 мс — 5,1 с.
- По умолчанию виртуальное время начинается с начала текущего реального часа (UTC); можно задать `virtualStart`.
- `asOf` оценки риска = виртуальное время прогона, а не время последнего измерения: если станция замолчала, её данные «стареют» относительно часов прогона, и модуль риска это видит (`STALE_DATA`).
- Каждый ответ о риске и измерениях содержит `context`: `mode` = `LIVE` (прогон идёт) / `PAUSED` (создан или на паузе) / `HISTORICAL` (прогон завершён или остановлен, проверочные данные T2, запрос с `at`) / `NO_DATA`; а также `virtualTime`, `realTime`, `lastReceivedAt`. Так старые данные не выдаются за актуальные.
- Почему в T2 было `ageH: 0` для данных от 02.04.2026: возраст считается от виртуального времени прогона (`asOf` = 02.04 12:00), а не от реального 28.10. Расчёт правильный, но раньше не было видно, что данные исторические; теперь это показывает `context.mode = HISTORICAL`.

### 6.1 Состояния и команды
```
             POST /runs                 start                  pause
  IDLE ───────────────────► CREATED ────────────► RUNNING ◄─────────────► PAUSED ──step──► PAUSED (+1 тик)
   ▲    POST /start {сценарий} ───────────────────►  │        resume         │
   │                                                 │ последний тик         │ stop
   │                                                 ▼                       ▼
   └───────────────── reset ◄─────────────── COMPLETED                   STOPPED
```
- Состояние симулятора = статус активного прогона (`sim_control.run_id`); `IDLE` — активного прогона нет. Статус, тик и скорость хранятся у прогона в `sim_runs`.
- **Остановка (stop)** — прогон завершается окончательно (STOPPED), данные остаются и доступны как история; приём телеметрии для него закрыт (`409 RUN_NOT_ACTIVE`).
- **Сброс (reset)** — если прогон ещё идёт, он останавливается; симулятор возвращается в IDLE. **Данные не удаляются.** Удалить завершённый прогон целиком может только администратор (`DELETE /api/simulation/runs/:id`).
- Недопустимые команды → 409 с кодом (`ALREADY_RUNNING`, `RUN_PAUSED`, `NOT_RUNNING`, `NOT_PAUSED`, `NO_ACTIVE_RUN`, `ACTIVE_RUN_EXISTS`).
- Все команды и тики выполняются **строго по очереди** (одна очередь в исполнителе): пауза не может «вклиниться» в середину тика; таймер максимум один.
- Ошибка доставки пакета (например, сбой БД) → прогон встаёт на паузу с `lastError`, бесконечных повторов нет.
- Перезапуск сервера: прогон, который шёл, переводится в PAUSED (`lastError = SERVER_RESTART`); после «Продолжить» следующий тик вычисляется заново детерминированно, дублей нет.
- Ограничения роста БД: не более 50 прогонов (`RUN_LIMIT`), не более 1000 тиков в прогоне, 200 вмешательств на прогон; запись о неверном токене устройства — не чаще раза в минуту.

### 6.2 Детерминизм
Шум не хранит состояние: `noise = σ · (2·u − 1)`, где `u = hash(seed | станция | параметр | тик)` (FNV-1a + перемешивание mulberry32). Любой тик вычисляется заново одинаково; одинаковые `scenario + params + seed + вмешательства` ⇒ одинаковые ряды (проверено тестами, в том числе после перезапуска).

### 6.3 Модель паводковой волны (учебная, не гидродинамика)
```
Исток (sourceStation, QRG-01): clean(t) = base + A·pulse(t − t0) + вмешательства(t)
pulse — трапеция: рост T_rise ч до 1, плато T_peak ч, спад T_fall ч до 0
Нижняя станция k:              clean_k(t) = base_k + α_k · среднее_{j<w_k}( clean_{k−1}(t − τ_k − j) − base_{k−1} )
                                            + L_k · pulse(t − t0 − Στ) + вмешательства_k(t)
Показание уровня:              clean + a_d·sin(2πt/24) + noise   (округление до 0,1 см, в пределах 0…1500)
```
- По цепочке передаётся `clean` (без шума и суточного колебания) — шум не накапливается.
- У каждой станции свои параметры (таблица `stations`): базовый уровень, `travel_hours` τ (51 / 51 / 17 ч), `attenuation` α (0,95 / 1,05 / 0,9), `response_hours` w — сглаживание (6 / 6 / 3 ч): ниже по течению волна растянута и плавнее.
- Учебные коэффициенты: a_d = 1 см, σ = 1 см. Сначала было 3 и 2 см: наклон от колебаний доходил до 0,8 см/ч > ε = 0,5, и риск «мигал» LOW ↔ MEDIUM на спокойной воде (ADR-019).
- Осадки — события сценария у конкретной станции; температура — общий тренд + суточный ход + шум 0,3 °C.

### 6.4 Сценарии [ТЗ §5.2: минимум «норма» и «опасное событие»]

| ID | Уровень (A; t0/T_rise/T_peak/T_fall, ч) | Осадки | Температура | Тиков | Результат (проверен тестами) |
|---|---|---|---|---|---|
| `NORMAL` | A = 0 | морось 0,5 мм/ч с вероятностью 5 % | −3 °C, суточный ход ±2 | 72 | уровни в пределах базового ± 2 см, все станции LOW |
| `GRADUAL_FLOOD` | 170; 10/24/12/48 | QRG-01: 2 мм/ч, тики 4–9 | −2 → +1 °C за 24 ч | 240 | пики 470 / 441,5 / 489,6 / 412,6 см — каждая станция по очереди выше W → MEDIUM, HIGH не возникает |
| `RAPID_FLOOD` | 300; 10/18/24/60; приток QRG-03 +40 см | QRG-01: 4 мм/ч, тики 4–9 | −4 → +8 °C за 24 ч | 260 | QRG-01 MEDIUM по дождю на тике 8 — до подъёма воды; пики 600 / 565 / 659,25 / 565,3 см; все станции по очереди HIGH |

Начало подъёма без шума: тики 11 → 62 → 113 → 130 (задержки 51 + 51 + 17 ч). При создании прогона оператор может изменить `amplitudeCm`, `startTick`, `riseH`, `peakH`, `fallH`, `totalTicks`, `levelNoiseCm`, `levelDailyAmplitudeCm` (с проверкой диапазонов). Сценарий сбоев данных (`SENSOR_FAULTS`) — в T8.

### 6.5 Ручное вмешательство
`POST /api/simulation/interventions` (оператор), только при активном прогоне. Вмешательство всегда действует **со следующего тика** (`effective_tick = current_tick + 1`): прошлое не меняется, записи не конфликтуют.

| Тип | Что делает | Передаётся вниз по реке |
|---|---|---|
| `LEVEL_SHIFT {stationCode, value}` | сдвиг уровня станции на value см (−300…+300), действует постоянно | да (входит в `clean`) |
| `RISE_RATE {stationCode, value, durationH}` | дополнительный рост value см/ч (−50…+50) в течение durationH ч (1…72), затем уровень держится | да |
| `MANUAL_READING {stationCode, parameter, value}` | одно ручное показание (наблюдение оператора) вместо сгенерированного в этом тике, `source = 'manual'`; повторный ввод на тот же тик заменяет значение | нет (это показание датчика, а не изменение реки) |

Значения проверяются (диапазоны параметра, наличие датчика у станции); каждое вмешательство пишется в `sim_interventions` и `audit_log` и учитывается при воспроизведении прогона.

## 7. Приём телеметрии [ТЗ §5.3]

`POST /api/telemetry`, заголовок `X-Device-Token`:
- **токен встроенного симулятора** — случайный при каждом запуске сервера, хранится только в памяти, наружу не выдаётся; обязательны `runId` и `tick`, `measuredAt` должен совпадать с виртуальным временем тика, тик — не дальше следующего;
- **токен устройства станции** — в БД хранится только SHA-256 (`stations.device_token_hash`, выпуск — T6); данные привязываются к активному прогону (иначе `NO_ACTIVE_RUN`), только своя станция, `measuredAt` не позже часов прогона, источник `device`.

```json
{ "runId": 3, "tick": 41, "records": [
  { "stationCode": "QRG-01", "parameter": "water_level", "value": 512.4, "unit": "cm", "measuredAt": "2026-10-30T00:00:00.000Z" } ] }
```
Проверки каждой записи (непрошедшие не сохраняются, пишутся в `device_log`, ответ перечисляет индекс и код): `UNKNOWN_STATION`, `STATION_DISABLED`, `STATION_MISMATCH`, `UNKNOWN_PARAM` (нет такого датчика у станции), `REJECTED_UNIT`, `REJECTED_RANGE`, `REJECTED_TIME`. Дубликат (`UNIQUE(run_id, station_id, parameter_code, measured_at)`) повторно не сохраняется и считается в `duplicates` — повторная отправка безопасна. Запись раньше последней в ряду → `quality = 'late'`; скачок больше `max_step` → `quality = 'suspect'` (окончательно решает модуль риска).

Затем **в той же транзакции**: часы прогона (`current_tick`) → `last_message_at` станций → оценка риска всех станций на виртуальное время этого тика (верхняя раньше нижней) → сохранение в `risk_assessments` (полная оценка — в `assessment_json`). При любой ошибке откатывается весь пакет. После фиксации — снимок в WebSocket.

Ответ: `{ runId, tick, virtualTime, accepted, duplicates, rejected: [{ index, code }], risks: [{ stationCode, risk, score }] }`.

**Состояние источников** [ТЗ §5.7] (T8): по `last_message_at` (реальное время): `ONLINE` — не дольше 3 × `tick_ms`, `STALE` — до 10 × `tick_ms`, `OFFLINE` — дольше.

## 8. Модуль оценки риска [ТЗ §5.4]

**Базовый вариант ТЗ:** прозрачные правила + весовые коэффициенты + оценка тренда. Это **не ML и не научно подтверждённый прогноз**; в интерфейсе постоянно видна пометка «Учебная модель, демонстрационные данные».

Реализация: `packages/shared/src/risk/` (чистые функции, без БД и сети) · загрузка данных из БД — `apps/server/src/risk/service.ts` · тесты — `packages/shared/test/risk.test.ts`.

Параметры (учебные, хранятся в `risk_config`, меняет admin; недостающие поля берутся из значений по умолчанию): `N = 6`, `N_min = 3`, `ε = 0.5 см/ч`, `J_max = 50 см/ч`, `maxGapH = 3 ч`, `staleAfterH = 3 ч`, `accelerationCmH = 2 см/ч`, горизонт прогноза `H_f = 3 ч`, `H_high = 6 ч`, `H_med = 24 ч`, `etaMaxH = 72 ч`, `H_up = 72 ч`, `P1 = 10 мм`, `P2 = 20 мм` (осадки за 6 ч), `T_melt = +2 °C` (средняя за 24 ч).

Оценка делается **на момент `asOf`** (модельное время): точки позже `asOf` не используются (`FUTURE_POINTS`) — расчёт прошлого не «подсматривает» в будущее. Время в расчётах — настоящие часы между измерениями, а не номер точки, поэтому неравномерные интервалы учитываются правильно.

### Шаги для станции
0. **Очистка:** отбрасываются нечисловые значения и неверные даты (`INVALID_POINTS`), точки после `asOf` (`FUTURE_POINTS`); из точек с одинаковым временем остаётся последняя (`DUPLICATE_TIMESTAMPS`).
1. **Окно уровня:** последние N измерений `water_level`. Если внутри окна разрыв больше `maxGapH`, точки до разрыва отбрасываются (`DATA_GAP`).
2. **Выбросы** (допустимый скачок `J = J_max · max(1, Δt)`; сравнение с последней принятой точкой): точка j (не последняя) — одиночный выброс, если `|h_j − h_prev| > J` и `|h_{j+1} − h_prev| ≤ J/2` → исключается (`SPIKE_IGNORED`). Последняя точка со скачком `> J` — неподтверждённый скачок: расчёт по предыдущей точке, доверие LOW (`SPIKE_UNCONFIRMED`). Скачок, после которого уровень не вернулся, принимается (`SUDDEN_JUMP`).
3. **Скорость** — наклон МНК: `v = Σ(t−t̄)(h−h̄) / Σ(t−t̄)²` (см/ч), `SE = sqrt(Σres²/(n−2) / Σ(t−t̄)²)`. Если точек < N_min → `v = null`, тренд UNKNOWN (`INSUFFICIENT_DATA`).
4. **Тренд:** RISING при v > ε; FALLING при v < −ε; иначе STABLE. **Ускорение:** при полном окне (6 точек) сравниваются наклоны по первым и последним 3 точкам; разница > `accelerationCmH` → ACCELERATING (`ACCELERATING_RISE`), < −`accelerationCmH` → DECELERATING (`DECELERATING_RISE`).
   **Устаревание:** если последнее измерение старше `staleAfterH` (`STALE_DATA`), прогноз и ETA не выдаются, фактор тренда = 0; фактор уровня считается по последнему известному значению с пометкой STALE.
5. **Прогноз на горизонт H_f = 3 ч** (от `asOf`, с учётом возраста a последней точки): `h₃ = h + v·(a + 3)`, диапазон `h + (v ± SE)·(a + 3)`. Статусы: OK / INSUFFICIENT_DATA / STALE_DATA / NO_DATA.
6. **ETA до опасного порога D** (часы от `asOf`): `h ≥ D` → ALREADY_EXCEEDED, 0; данных мало/устарели → UNAVAILABLE; не растёт → NOT_EXPECTED; порог не задан → NO_THRESHOLD; иначе `(D − h)/v − a`, диапазон `[(D−h)/(v+SE) − a, (D−h)/(v−SE) − a]` (правая граница null, если `v − SE ≤ ε`). Если ETA > `etaMaxH` — **число не называется** (BEYOND_HORIZON): линейная экстраполяция на такой срок ненадёжна.
7. **Доверие:** LOW — нет уровня, < N_min точек, неподтверждённый скачок или данные устарели; HIGH — n = N и SE ≤ 0.25·|v|; иначе MEDIUM. Ускорение/замедление, разрыв, отброшенный выброс или резкий скачок понижают HIGH до MEDIUM. Итог — в `dataQuality` вместе со статусом данных (OK / DEGRADED / INSUFFICIENT / STALE / NO_DATA) и списком замечаний.
   Диапазоны отражают только статистический разброс последних точек, но не ошибку самой линейной модели.
8. **Факторы и баллы** (весовые коэффициенты по умолчанию; каждый фактор — причина с параметрами):

| Фактор | Условие → баллы | Код причины |
|---|---|---|
| F1 Уровень | h ≥ D → 4; h ≥ W → 2; иначе 0 | `LEVEL_ABOVE_DANGER` / `LEVEL_ABOVE_WARNING` |
| F2 Тенденция | RISING и (порог превышен или ETA ≤ H_high) → 3; RISING и ETA ≤ H_med → 2; RISING → 1; иначе 0 | `ETA_DANGER_WITHIN{hours}` / `RISING{rate}` / `ETA_BEYOND_HORIZON` |
| F3 Осадки | сумма за 6 ч ≥ P2 → 2; ≥ P1 → 1 (сумма = Σ интенсивность × интервал до предыдущего измерения) | `HEAVY_RAIN{mm}` / `MODERATE_RAIN{mm}` |
| F4 Температура | средняя за 24 ч ≥ T_melt → 1 | `SNOWMELT{temp}` |
| F5 Волна сверху | верхняя станция HIGH и τ ≤ H_up → 2; MEDIUM и τ ≤ H_up → 1 | `UPSTREAM_WAVE{station, hours}` |

Нет данных по параметру → фактор 0, статус NO_DATA, причина `NO_DATA{parameter}`; нет датчика у станции → NO_SENSOR; у станции нет верхней → NOT_APPLICABLE. Каждый фактор возвращается с баллом, максимумом, значением, единицей и причиной; сумма баллов факторов = итоговый балл (максимум 12).

9. **Категория:** HIGH, если `h ≥ D` или `score ≥ 5`; MEDIUM, если `score ≥ 2`; иначе LOW.
10. **Результат** (`RiskAssessment`): модель (`QORGAN-RULES-1`, пометка demo, версия `risk_config`), `asOf` и `computedAt`, категория, балл и максимум, уровень с порогами W/D и возрастом, тренд (скорость, SE, ускорение, окно), прогноз на 3 ч, ETA, факторы с вкладом, причины (сначала самые весомые), качество данных. Все числа округлены и конечны.

## 9. Предупреждения [ТЗ §5.6]

- Срабатывание: риск станции стал MEDIUM/HIGH и активного предупреждения нет → `OPENED`. Поля: время, станция, тип ЧС (`flood`), уровень (`severity`), причина (`trigger`: `DANGER_LEVEL` при h ≥ D, иначе `FORECAST` — «ухудшение прогноза»), список факторов.
- MEDIUM → HIGH: то же предупреждение, `ESCALATED`; HIGH → MEDIUM — `DEESCALATED`.
- Риск LOW 3 обработки подряд → условие снято (`CLEARED`, `is_active = 0`). Новое ухудшение после этого → новое предупреждение.
- Оператор: «Просмотрено» (NEW → VIEWED), «Обработано» (→ RESOLVED, комментарий). Отметки не зависят от `is_active`: тревогу можно обработать, пока условие действует.
- Дубли исключены уникальным индексом «одно активное предупреждение на станцию в прогоне» и транзакцией.

## 15. Надёжность, резервное копирование, восстановление [ТЗ §9 «Надёжность»]

- Проверка данных: §7 (телеметрия), zod-схемы на всех входах API, CHECK-ограничения в БД.
- Ошибки: единый обработчик Fastify → понятный код; фронтенд показывает сообщение, а не «белый экран» (error boundary).

- Резервная копия: `VACUUM INTO data/backups/qorgan-ГГГГММДД-ЧЧММ.db` (`npm run db:backup`, кнопка в Admin). Полный сброс: `npm run db:reset`.
- Код: коммит после этапа, тег `checkpoint-*` перед рискованными изменениями; `git push` — только с разрешения.

## 17. Источники данных, допущения, ограничения [ТЗ §10]

- **Источники:** геометрия реки и населённых пунктов — OpenStreetMap (ODbL); подложка — OpenFreeMap. Показания — **только симулятор**.
- **Допущения:** задержка волны пропорциональна расстоянию (3 км/ч); линейное ослабление/усиление волны и сглаживание скользящим средним; 1 тик = 1 виртуальный час; дождь и потепление увеличивают риск по фиксированным баллам; пороги W/D выбраны учебно.
- **Ограничения точности:** диапазоны прогноза и ETA учитывают только разброс последних 6 ч, но не ошибку модели; одиночный выброс в первой точке окна не распознаётся; линейная экстраполяция на 3 ч не учитывает нелинейную динамику, лёд, дамбы, водохранилище, приток притоков; коэффициенты не откалиброваны на реальных данных; качество прогноза не измерено. Система — учебный прототип, не сертифицированная система оповещения [ТЗ §11].
